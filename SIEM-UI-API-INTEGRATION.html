SIEM connectors — what to call for every tile

The SIEM backend is already built — both halves (push Destinations and pull API access), the 5-step connect wizard, secret rotation with overlap, and the OAuth + events feed. This maps each screen element to its endpoint, flags the few gaps, and lists the small items left to build.

Routes are shown without the gateway prefix. The public URLs the collector uses (/dlp/oauth/token, /dlp/siem/events) carry the /dlp APIM prefix; console routes are [Authorize] JWT like the rest of the app. All list/save calls use the standard ApiResponse envelope; /oauth/token and /siem/events return raw (RFC-6749 / feed JSON).

B · Connect-a-SIEM wizard (5 steps)

Step 1 — Vendor

GET siem/providers → { key, displayName, endpointLabel, secretLabel, setupSummary, isImplemented, defaultFormat, extraFields[] }. Implemented: splunk-hec, sentinel-dcr, qradar-syslog, webhook. have — Elastic / Sumo Logic / Google SecOps "coming soon" cards are missing (Build #2 adds them as isImplemented:false).

Step 2 — Credentials

POST siem/connectors — body { provider, displayName, endpointUrl, secret, config{…}, format, sensitivePolicy, filterJson }. Per-vendor non-secret fields go in config, keyed exactly as extraFields[].key from step 1 (Splunk: index, sourcetype; Sentinel: tenantId, clientId, dcrImmutableId, streamName; webhook: headerName; QRadar: caCertificatePem, no secret). Secret is encrypted on write, never returned (only secretHint = last 4). Saved isEnabled:false, status:Pending. have

Step 3 — Filter (severity + event types)

Stored as filterJson on the connector; empty/{} = send everything. partial — the rule engine understands Severity and PolicyAction, but there is no severity enum endpoint and no event-type catalog, so the UI can't yet map its 5 checkboxes server-side. Build #3 defines this. Until then the shape the UI must emit is:

{ "op":"AND", "rules":[
    { "op":"IN", "field":"Severity", "value":["Critical","High"] },
    { "op":"IN", "field":"EventType", "value":["BlockedTransfer","PolicyViolation"] }
] }

The EventType field and its values (Blocked transfers / Policy violations / Approval decisions / Discovery findings / Agent health) need server-side definition — that's Build #3.

What's left to build

Everything above marked "have" is ready for the UI today. These close the gaps:

  1. Sent-24h + queue on the list row. Add sentLast24h and backlog to siem/connectors/list rows so the grid shows "Sent 24h" and derives the queue text without an N+1 to /health. small API
  2. "Coming soon" vendors. Add isImplemented:false descriptors for Elastic / Sumo Logic / Google SecOps to siem/providers so the greyed cards render. small API
  3. Filter contract. Define the event-type catalog (Blocked transfers / Policy violations / Approval decisions / Discovery findings / Agent health → EventType values) and the severity enum, and either expose a filter-schema endpoint or lock the filterJson shape above. Needed before the UI can wire step 3. needs a design call
  4. "Category summary" sensitive mode. ✅ Done — sensitivePolicy = "summary" emits category counts ({"PII":2}), never a value; constraint widened (V0052). shipped
  5. Allowed-IP enforcement. Enforce allowedCidrs at oauth/token / the events auth — today the field is stored but ignored (a security gap, not just UI). security
  6. Last-used stamping. Record lastUsedUtc on each successful siem/events call so the column isn't permanently blank. small API
