The one idea

Every clickable thing in the design — tiles, bars, donut segments, legend rows, heat-map cells, insider cards, user chips — opens the same panel. So there is one drill-down endpoint, not one per widget. The only thing that changes is the filter you send.

Total Incidents and Policy violations are the same call. Both are {"actions":["Blocked","Warned","Override"]}. They are two tiles onto one set of events, so their numbers must agree.
The filter composes — this is the important part. The user chips inside the panel are clickable. Clicking "Mac Ferrari" re-opens the panel as the filter you already sent, plus that user. So keep the filter object you used, add userIds, and send it again. Keep a stack of them and you have the back button for free.

Conventions

HeaderRequiredNotes
ClientGUIDyesTenant identifier.
AuthorizationyesBearer <jwt> — all of these need a login.
Content-Typeyesapplication/json. Every endpoint is POST.
Names are trimmed; absent text is null, never "". The agent pads what it sends, so names arrived as "balamaruthi.n " and unset emails as "". Both are cleaned at the edge now, across every endpoint — userName, name, email, app. Treat null as "we do not have one" and render your own placeholder; an empty string will not appear.

All responses use the standard envelope { "success", "message", "data", "errors" }. The samples below show data only. Dates are ISO-8601 UTC. A date with no time means the whole of that day.

Casing: responses are camelCase. success, totalIncidents, blockedPercent — exactly as written in the samples here. Confirmed against a raw body off Kestrel on QA, not inferred.

One serializer serves the whole API and no endpoint configures its own, so all thirteen agree. Requests are case-insensitive — fromDate and FromDate both bind — so only responses were ever in question.

An earlier revision of this page claimed PascalCase. That was wrong, and wrong for a specific reason worth recording: it reasoned from Newtonsoft's own default rather than from what ASP.NET Core configures on top of it. Every sample has been corrected.
Every endpoint takes the same filter object. All thirteen accept the full filter — not just fromDate/toDate. So the header's Severity, Action, Department and Search controls are applied by sending the same body to every call on the page; there is nothing to filter client-side.

splitBy, channel and category are body fields, not query parameters. One payload object per call, always.
Five endpoints were ignoring all of that and no longer do. time-series, overview/risk-score, activity-heatmap, exfiltration/breakdown and classification/breakdown were reading their tables with only a date range, so they returned the same numbers whatever you sent.

time-series also honours areas now — ["web"] was still counting every file and content event, which is where 22,041 "Blocked" came from against a web tab showing 1,071 requests.

One exception, by necessity. overview/risk-score reads the daily risk snapshots, and a snapshot carries a user and a date and nothing else the filter speaks of — no severity, no channel, no app. It honours departments / userIds and the dates; the rest cannot apply, because the score was computed before those distinctions existed. That is why it no longer reads 60 for a department nobody is in.

1. Drill-down — the panel behind every click

POST/dashboard/v2/drill-down
Example — clicking "Total Incidents"
curl -X POST "{dlp-api}/dashboard/v2/drill-down" \
     -H "ClientGUID: …" -H "Authorization: Bearer <jwt>" \
     -H "Content-Type: application/json" \
     -d '{ "actions": ["Blocked","Warned","Override"],
           "fromDate": "2026-10-20", "toDate": "2026-10-26" }'
Response

  ],

Why BusinessHours and TimeZone are in the response. Off-hour activity is measured against the customer's own configured hours. When someone questions the number, show them these two fields — that is what produced it.
The change badges: what they compare against. The window immediately before the one you asked for, of equal length. Ask for 20–26 Oct and the baseline is 13–19 Oct. Every other filter stays applied — a Finance-only view is compared against Finance last week, not the whole company.

null means no comparison is possible: either the previous window had nothing, or you sent no dates at all (an open-ended window has no "before"). Render nothing in that case — "↑ 100%" from a zero baseline is noise, so the API declines to say it.

3. Activity heatmap

POST/dashboard/v2/activity-heatmap
{
  "cells": [ { "dayOfWeek": 1, "hour": 9, "count": 14 } ],
  "max": 31,
  "timeZone": "Asia/Kolkata"
}

dayOfWeek is 0 = Sunday. hour is 0–23 in the customer's local time, not UTC. Use max to scale your shading.

Only non-empty cells are returned. A weekday/hour with no events is absent from the array rather than present with zero — render your 7 × 24 grid and fill from what arrives.

Each cell is a click target: send its dayOfWeek and hour to drill-down as daysOfWeek and hours.

Largest Transfers rows open. Each carries eventId and area — send both to event-detail. They are the only ranked rows that do: every other list is a group of events, so there is no single event to open and the fields are null.

Rows are de-duplicated on file, size and user, because a transfer that was crunched twice — a retry or a re-scan — listed as two identical incidents. Anything still appearing twice is two real events, and the differing eventId proves it. label is the file name. sublabel is "User · App", and just the user when the row names no app — the channel used to stand in for it, which read as an application called "Upload".

topDeviceTypes rows carry writes and reads as integers for the two bars; the same split is in sublabel as text, so there is nothing to parse out of a string.
Device Read and Device Write now carry their events. They were reading 0 while the device card beside them listed thousands, and the Upload figure was inflated by every one of them. The cause: a removable-device transfer is not stored with its own activity type — the agent sends Upload or Download and sets a device flag. Direction follows the same rule the policy engine uses: writing to the device is an upload, reading from it is a download.

Upload and Download will drop by the amount Device Write and Device Read gain, and totalEvents is unchanged — the events were always there, on the wrong row. channels: ["device_write"] now filters correctly too, and ["upload"] no longer sweeps up USB writes.
The design shows individual devices ("SanDisk Ultra 64GB"); we return device types — USB, Bluetooth, NAS. The agent does not send a serial or volume label, so individual devices are not available. Label the card accordingly.
dataClassification is this tab's own card. File events only, so it will not match the Overview card of the same name, which covers all three areas. Same row shape as that card, so one component renders both. violatedBytes is the volume that tripped a policy — a blocked transfer never left the building, so this is not "data exfiltrated".

Send code, not label, when a row is clicked — {"dataTypes":["CODE"]}. The label is reworded freely; the code is not. A file carrying both PII and PCI is counted under each, so the rows sum to more than totalEvents.

The detail panel for a content event is specified to show a character count. We do not store one — that field is absent. Hide it until the agent change lands.
topUsers: count is all that user's content events, and the list is sorted by it. So "by content events" is the right caption. blockedCount is the subset that was blocked — Pravin R's 490 events of which 468 blocked. It was sorted by blocked while showing the total, which made neither number explain the order; the sort is the number on screen now.

Not severity: content events carry none — the scanner does not assess a paste or a prompt — so the original "Critical or High" ranking matched nothing and the card was empty.
responseOutcome has four rows, and Override is the fourth. This is the only tab it can appear on — a file transfer has no override flow — and it is why the card's rows used to sum to less than totalEvents with nothing accounting for the difference. See Override for what it means.
topAiTools is restricted to the app catalogue's GenAI tools — ChatGPT, Claude, Gemini, Copilot, Perplexity, DeepSeek, Grok. The underlying field is "whatever application the agent saw the prompt in", which is why Teams, mail.google.com and a browser-extension id were appearing in a list captioned Top AI Tools. Prompts captured elsewhere are still counted in totalEvents; they are just not AI tools.

One row per tool, not per way of reaching it. "Claude" and "claude.ai" are the desktop app and the website; every alias the catalogue lists — display name, domains, process names — folds into the tool's display name, so its count is whole rather than split across two rows.
sensitiveDataDetected resolves through the sensitive catalogue, item level included. The stored column mixes category codes (pII, FIN_RECORDS) with individual detector names upper-cased (EMAIL ADDRESS), and both now land on the category: "Personally Identifiable Information", counted once.

A trailing qualifier is stripped only if the full value matches nothing, so NATIONAL ID (INDIA AADHAAR) resolves via "National ID" while a catalogue entry that legitimately has brackets — "Tax identification (GSTIN)" — still matches whole.

A name the catalogue has never heard of keeps its own row. It is given presentable casing ("Person Name (With Label)") but is not assigned to a category on a resemblance. If one of those should sit under PII, the fix is a row in policyv2."SensitiveItem", not a guess here.
department is today's department, not the one at the time of the event. The event does not carry a department, so it is read from the user record; someone who changes team takes their whole history with them. sublabel is the two pre-joined for the "Dept · email" line, so you can bind one field or the two separately.

Categories account for every request now. Rows with no category were being dropped, so the card showed 92 of 1,071 with nothing explaining the other 979 — most browsing matches no category. They are grouped under a single Uncategorised row, which sorts last however large it is so it cannot push the real categories off the card. TopBlockedDomains[].Sublabel says Uncategorised for the same reason, instead of being null.

That row is clickable like any other. {"areas":["web"],"categories":["Uncategorised"]} returns the requests that matched no category. It is not a stored code — those rows have no category at all — so the value is given its meaning by the API; send it exactly as the row's code gives it.
topBlockedDomains is one row per domain. It was grouped by domain and category, and the category is recorded per request — so chatgpt.com appeared twice, 146 blocks as Uncategorised and 40 as Computers And Technology, with its real rank split between the two rows.

Each domain now has a single row carrying its full block count, and sublabel / code report the category most of those blocks carried — a label on the row, not what the row counts. A domain whose requests are categorised inconsistently therefore shows one category while its count includes the rest; that is the trade for a rank that means something. When you send the row to drill-down, filter on domains, not on its code.
A severity or data-type filter empties this tab. Web requests carry neither, so a header set to "Critical only" returns TotalRequests: 0 here rather than ignoring the filter. The same goes for channels, devices and minSizeBytes, which are about file traffic. That is deliberate: silently ignoring a filter shows numbers that contradict the control the user just set.
Two things on this tab. The severity columns in riskByCategory are always zero — a web request carries no severity, so only Events and Stopped are meaningful; render the row without the severity bar. And "Warnings Bypassed" is not here: nothing records that a user continued past a warning. Leave that card out.
These numbers will not match the Logs screen's "Web Filtering" filter. That filter means sensitive data that reached a website; this tab means policy-matched browsing. Two different populations, same words. Expect the question.

Endpoint Coverage's "Warning" is derived, not stored — it means online but the DLP service is not running. There is no Warning status in the database; this is the closest real signal, so label it carefully.
The coverage buckets now add up. Healthy + Offline + Warning + NotReporting = TotalEndpoints, always.

notReporting is new and it is why they did not before: those are active endpoints that have never sent a status — registered, never heard from. They are kept as their own figure rather than folded into Offline, which would claim we had watched them go quiet, or into Healthy, which would claim they are protected. Nine silent machines out of 58 is a finding worth drawing.

healthyPercent is now a share of all active endpoints rather than of those reporting, so a fleet that is mostly silent cannot read as 100% healthy.
Security Score's policy ratio is coherent. policiesNeedingReview could exceed totalPolicies — 28 of 26 — because the two were counted from different populations: the total from the policy tables, the review count from policy names appearing in the logs. The log carries free-text PolicyName and no PolicyId, so it also holds names that were renamed, deleted, or never matched an active policy.

Needing-review is now counted only among the policies totalPolicies counts. Noise from a policy nobody can open is no longer reported as a policy to review, so this figure can only go down — and it can never again exceed the total.
One Compliance number on the screen, not two. securityScore.compliancePercent counted file and content only while the headline policyCompliancePercent counted those and web requests, so the Overview showed 15% on the card and 11% in the tile for the same window — the gap being the web traffic, which is almost entirely blocked. Both are now counted over all three areas and the two must agree exactly.

policiesNeedingReview moved with it: a policy's noise is counted across the activity log and the web-filtering log together, so a web policy that blocked several hundred requests is now named by the card that scores it. Expect this figure to rise on tenants with active web policies.

POST/dashboard/v2/classification/breakdown

"Select a category to see identifier breakdown" on the Data Classification card.

{

    { "label":"Aadhaar Number", "count":24, "sizeBytes":942669824, "percent":38 },

Identifier names only — never the matched values. The values are the sensitive data itself; a dashboard that returned them would become a second copy of everything it was built to protect.
Two categories do not look like the others. cODE has no identifier labels at all — it stores language-tagged snippets, so the rows come back as the detected languages ("JAVASCRIPT", "C#"), which is the only identifier-shaped thing in there.

A category can also come back with fewer rows than it has files. Entries stored as a bare value with no Label= are dropped rather than guessed at — that is what "10.40.0.0/16" and "PROD" were, and a value must not reach this card even when it costs a row.

Names are returned as display names throughout: PII_EMAIL reads "Email", and it merges with rows already stored as "Email" instead of listing twice.

Punctuation variants merge too. "Credit/Debit Cards" and "Credit Debit Cards" are one identifier written two ways by different parts of the pipeline; they are now one row carrying the combined total, labelled with the punctuated spelling.

Saved widget layout — one per tab

POST/UserSync/SaveUserDashboardWidget

Drag-and-drop layout now stores which tab a widget sits on.

Confirmed: tab on each widget is enough. The save reads the tab from the widget first and falls back to the request-level tab, then to "overview". Both shapes work, and you can send a mixed payload — the save then covers exactly the tabs it mentions.

Click → filter map

What to send to drill-down when each element is clicked. The filter you send is also the one you push onto your back-stack.

The tab you are on is part of the filter. Always send it. drill-down is one endpoint over all three populations, and the request is the only thing that tells it which one you mean — there is no tab in the URL, no session state, nothing to infer from. A click on a File Sharing widget that omits areas asks about file and content, and the panel comes back with AI-prompt rows in it. That is the endpoint answering the question it was asked, not a server bug.

The rule: every click that originates on a tab carries that tab's areas — ["file"], ["content"] or ["web"] — on top of whatever the widget itself contributes. Only Overview widgets are genuinely cross-area, and they are the only ones that may leave areas out.

Where the widget's own filter already implies the area — channels:["upload"] can only be file, channels:["prompt"] can only be content — sending areas as well is redundant but harmless, and it costs less than remembering which cases are which. Send it everywhere.

Two Overview rows carry two numbers, and each needs its own filter.

A High-Risk Users row shows violations — Blocked, Warned and Override file or content events for that person — beside criticalCount and highCount, which count only the events the scanner graded. The severity body reproduces the second pair, not the first, so sending it for a click on the headline number returns a fraction of it and looks broken. Both bodies are listed above; send the one that matches the figure the user clicked.

Top Incidents by Apps counts incidents, not events, so its filter needs the three incident actions. It is also drawn from file and content only and excludes removable devices, which is why it carries areas — without it the panel adds web requests the card never counted.

Both cards used to count a fourth thing, and it is why they could not be matched. They counted everything that was not Allow, and the column has a fourth value — UnCovered, meaning no policy applied to the activity at all. That is the absence of a verdict rather than a violation, there is no actions value for it, and so no filter could ever reproduce a row that included it: six rows summed to 2,154 against a drill-down of 2,130. Both cards now count the three named outcomes, the same ones totalIncidents counts, and the figures agree exactly. Expect both to read slightly lower than in the previous build.

departments takes names, not ids — the same string the dropdown shows, matched against the user record. Combined with userIds it is an AND: "Engineering" plus a user means that user only if they are in Engineering, and a department nobody is in returns an empty result, not everybody.

It filters on where someone works now. The event carries no department, so someone who changes team takes their whole history with them.
Some combinations are empty by definition, and that is correct rather than a bug: a channels, devices or minSizeBytes filter excludes web requests, and a severities or dataTypes filter also excludes them — web requests carry neither.

Things to know before you build

  1. A drill-down without areas is not scoped to the tab you clicked from. One endpoint serves all three populations and the request is the only thing that names one, so a File Sharing widget that sends {"dataTypes":["PII"]} gets file and content back — the panel lists AI prompts under a File Sharing heading and the Events count is larger than the card that was clicked. Send "areas":["file"] with it. See the Click → filter map, which is now split per tab for exactly this reason.
  2. The clock filters work now — offHoursOnly, hours and daysOfWeek. All three were on this contract and read by nothing, so the Off-Hour Activity panel listed the whole window — 4,537 against a tile of 816 — and every heat-map cell opened the same unfiltered panel. They are evaluated in the tenant's time zone now, and the Off-Hour panel matches its tile exactly. If you had worked around this client-side, remove the workaround: the filters narrow for real, and a second filter on top of them will double-count nothing but will hide events. They read file and content only, the same population the tile and the heat map are drawn from, so a web area sent with them returns nothing by design.
  3. A fifth severity exists. The design draws four; the scanner also emits None when it could not assess a file, and it is often the largest bucket. Decide how to show it — but do not assume the four add up to the total.
  4. Three cards the design shows are not served: Violations by Regulation, Warnings Bypassed, and Departing Employee. Leave them out rather than rendering them empty.
  5. Endpoint Coverage has no "Warning" slice — endpoints are only Online, Offline or Locked.
  6. Keep a filter stack for the back button. The server returns no back pointer; the panel's history is yours.
  7. The drill-down panel's heading is yours to set. title and subtitle have been removed from the response — they were always empty, because one query serves many labels. Use the tile you clicked.
  8. A change badge of null means "do not render one". Not zero, not 100%. Either the previous window had nothing or no dates were sent.
  9. Copy / Paste and Typed Content are Content Sharing, not File Sharing. They were landing on the wrong tab because the underlying view labels every transfer row "File"; the tabs now split on the transfer type instead. If you compared tab totals against an earlier build, they have moved — the new numbers are the right ones.
  10. Per-tab layout needs migration V0016. Saving a tab layout fails until it has run on the tenant.
  11. Device events have moved off Upload. Device Write and Device Read were 0 and Upload was carrying their events. Both the KPIs and the channels filter are fixed — expect Upload to fall and the two device channels to rise by the same amount.
  12. Only Largest Transfers rows are clickable to an event. Every other ranked list is an aggregate, so eventId is null there by design.
  13. Total Incidents means Blocked + Warned + Override. It was "everything that is not Allowed", which counted a handful of Override events the drill-down's ["Blocked","Warned"] then excluded — 22,185 against 22,180. Both sides name the same three outcomes now, so send all three.
  14. event-detail needs the right area. The three populations have independent id sequences, so 4810 exists in all of them and means a different event in each. The area now selects the population before the id selects the row; sending the wrong one returns 404 rather than someone else's event.
  15. Risk by Channel always returns every channel, zeros included, so the table keeps its shape and a 0 reads as "nothing happened" rather than "not measured".
