B2

MachineName is the right key

Confirmed â€” keep sending MachineName.

The grid filter binds by reflection to the entity, and the entity column is MachineName. deviceName exists only on the DTO, where it is populated from MachineName. A key that binds to nothing is swallowed and the filter is skipped, which is why any value returned every row â€” a known rough edge in the generic filter, not something specific to this endpoint.

One trap: deviceName does not mean the same thing everywhere. On GetIncidentTransferLogs it is the machine. On the grouped GetTransferLogs views it is AppDeviceName â€” the application or USB device involved, a different column entirely. Filter the machine with MachineName on both.

B3

Use likeFilters for policyAction

Confirmed â€” likeFilters is correct, and the exact count is the one that is wrong.

policyAction is not a plain column. The value the grid shows is computed: ProcessStatus == "Completed" ? PolicyAction : ProcessStatus. An event still in flight â€” Under Review, Override Applied, Override Rejected â€” keeps Block in the raw column while the grid shows it under its process status instead.

We lift likeFilters.policyAction out of the generic pipeline and turn it into a SQL predicate that knows about that rule, and policyActionCounts is built from the same computed value â€” which is why the two always agree. exactFilters.policyAction is not lifted: it falls through to the reflection filter and matches the raw column, so it sweeps up rows whose displayed action is something else.

Your 308-row gap on Block, 204 on Allow and 1 on Warn is exactly that set. You can see it without changing anything: send exactFilters for Block and read policyActionCounts in the same response â€” Block reads 26,235 and the extra 308 appear under their process-status names.

This is an inconsistency on our side, not a second meaning. notExactFilters is already lifted the same way likeFilters is; only the positive exact filter was missed. Say the word and we will lift it so the two agree, but nothing about your integration needs to change.

B4

Grouped views need sortBy

Confirmed and expected. sortBy: "totalActivity" is the right fix.

The grouped views project a GROUP BY with no default ORDER BY, so PostgreSQL is free to return groups in any order â€” and may return them in a different order on the next call, which makes paging unstable as well as unranked. Only the event grid carries a tie-break of its own. Treat it as a rule for every grouped or paged grid you page through: no sortBy, no guaranteed order.
