4 · Who counts as an approver

You asked which role ids decide this. Read it from GetUserOverrideSettings — do not derive it yourself.

GET /exe/V1/GetUserOverrideSettings/{userId}

→ "isApprover": true,          ← show the Approvals tab
  "canDecide": true,           ← show the Approve / Reject buttons
  "roleIds": [3],              ← this user's role ids, for display only
  "pendingApprovalCount": 4    ← the tab's badge

  "maxSelfOverrideHours": 8,   ← "Your admin allows up to 8 hours"
  "maxAdminApprovalDays": 30,  ← "Up to 30 days, the team may shorten it"
  "typicalResponseTime": "2 to 4 Hours",

  "canSelfOverride": true,     ← on the POLICY route, can be false
  "canAdminOverride": true,
  "selfOverridesTotal": 3,     ← from the policy on the policy route
  "overrideResetPeriod": "Monthly"   ← Daily | Weekly | Monthly | Never

The last four vary by which route you call — see §5. On GetUserOverrideSettings they come from the older policy tables, as they always have; on GetUserPolicyOverrideSettings they come from the new published policy.

One behaviour change on the original route worth knowing: the allowance is now enforced on submit. It was previously read and displayed but never checked, so a user past their limit could keep going. The limit enforced is the same number you have been showing as "3 / 5".

The two ceilings are enforced, not just displayed — ask for longer and the submit comes back 409 LIMIT_EXCEEDED. Read them rather than hardcoding, so changing the number is a config edit instead of an agent release.

A user is an approver when both hold:

ConditionWhere it comes from
The user is activesfm."User".IsActive
Their role is mapped as an approval role on any policy — or their role name is DLP Admin dlp."PolicyApprovalRoleMap", written by the policy screen's approvalRoleIds. The DLP Admin fallback covers tenants that have never set an approval role, which would otherwise have no approvers at all — it is also already who receives the "please review this" notification.

pendingApprovalCount counts requests still awaiting a decision — admin approvals and large-file requests — across the tenant, not per policy. It is always 0 for a non-approver.

canDecide is a separate field but currently returns the same value as isApprover. It exists so view-only reviewers can be introduced later without you changing anything: bind the tab to isApprover and the buttons to canDecide, and that split will just start working.

Note it is per user, not per request row. With no per-policy scoping in effect today those are the same answer, so apply canDecide to every row.

5 · Things to know before you build

Copy Paste and Typed Content are not available.

Nothing in the activity log records whether content arrived via the clipboard or the keyboard, so the API cannot tell them apart — it would be guessing. Those rows keep whatever transfer type they were logged under. This needs the exe agent team to stamp the channel at capture. The other four values are correct and safe to bind to.

isApprover hides the tab; it does not protect the endpoint.

Use it to decide what to draw. The approvals endpoints still answer any caller — the tray app has no login, so the userId you send is a claim, not an identity. Real enforcement comes with the tray-app authentication work. Please do not treat the flag as a security boundary.

unlimited is in the contract but is always false.

You asked whether maxOverrideAttempts = 0 meant unlimited or not configured. Neither — it means zero. The column is nullable, so "not configured" is already NULL (and falls back to a default cap), which leaves 0 meaning zero attempts. Reading it as "no limit" would hand an infinite allowance to an administrator who set it to forbid overriding.

So the policy model currently has no way to say unlimited. The field stays in the response for you to bind to, and will start returning true if the policy screen ever grows a way to mean it. Until then, treat remaining/total as the truth.

Submit can now refuse you. This is new.

Requests that succeeded last week may now come back refused. Handle both:

400  NOT_ALLOWED        the policy does not permit this override, or not at
                       this activity's sensitivity
409  LIMIT_EXCEEDED     the allowance for the period is spent, or the duration
                       asked for exceeds the ceiling
409  DUPLICATE_REQUEST  a request for this activity is already open
409  ALREADY_DECIDED    another approver got there first — refresh, do not retry

Read data.errorCode, not the message — the wording will change, the codes will not. Both success flags say false on a refusal.

Nothing above changes on the endpoints you already call.

The policy-driven behaviour lives on separate routes, because moving to the new policy has not been agreed. Keep calling what you call today and nothing changes; switch the URL when you are ready. Request and response shapes are identical, so it is a URL change and nothing else.

unchanged, app settings          policy-driven
──────────────────────────       ─────────────────────────────────
SubmitOverrideRequest            SubmitPolicyOverrideRequest
GetUserOverrideSettings/{id}     GetUserPolicyOverrideSettings/{id}   (portal host)

One implementation underneath both, so the two cannot drift into different rules.

The original routes read the older policy tables, as they always have — so selfOverridesTotal and canSelfOverride still come from a policy there, just not the new one. What they do not do is check sensitivity, so NOT_ALLOWED never comes back from them, and the allowance is always counted over a calendar month whatever overrideResetPeriod says.

On the policy routes, a submit can be refused for reasons the previous screen did not show.

The Response options section of a published policy drives all of this:

Self override          off        → NOT_ALLOWED
Override attempts      3 per user → the 4th is LIMIT_EXCEEDED
Limit resets           Daily | Weekly | Monthly | Never
Applies to sensitivity Medium, Low → a Critical activity is NOT_ALLOWED
Admin approval         same toggle and sensitivity rules

Two consequences worth designing for. canSelfOverride can come back false — do not assume the route is always open. And a user who passes every check on the detail screen can still be refused on submit, because sensitivity is per activity: the same person may self-override a Low finding and not a Critical one under one policy.

overrideResetPeriod now returns any of the four values, not only Monthly. Never means the allowance never refills — it is a lifetime total, not unlimited — and nextResetAt is null for it.

Where no policy is published, all of this falls back to server config and behaves as it did before. If selfOverridesTotal comes back 5 with "Monthly", that is the fallback answering, not a policy.
