Scanner · Architecture note for design planning

How each source is scanned — and what platform-hosted coverage we still need

For the UX / product team. Captures the agent-vs-platform model across all five Scanner tabs, corrects the Network tab to its full source set, and lists the builds and design decisions ahead.

Status reflects the API + agent code as of this review. “Have / Partial / Missing” is verified against the repository, not planned work.

01The one principle: reachability decides who scans

Every source lands in one of two homes. Which one is not a preference — it is forced by whether our cloud can reach the data.

☁
Public / internet-reachable (SaaS, object-storage buckets, anything on a public IP) → our cloud scans it directly. Platform-hosted, nothing to install.
⌂
Private / internal (10.x, 192.168.x file servers and shares) → our cloud cannot reach it, so software must run inside the network: a scanner node (crawls many shares by IP) or a host agent (reads one server’s own disks).

02The “Network” tab is 5 source kinds × 2 methods

“Network” and “Server Scanner” are the same tab. The design’s add-flow is far broader than “install an agent on a server” — it offers direct-attached disks, SAN, SMB/NFS shares, cluster shares, and cloud buckets, scanned either by a host agent or a scanner node.

Partial (NAS/HCI): the host agent can read a UNC path if you list it in its settings — but there is no scanner-node model, no native NFS, remote-share encryption reads Unknown, and targets are local-config only (no console). Missing (buckets): our cloud clients are SaaS drives, not object storage — though the AWS S3 and Azure Blob SDKs are already referenced for our own storage, so AWS/Azure have a head start; GCS does not.

05Decisions & builds to plan around

  1. Network tab = four options, not one. Host agent (have) · scanner node (new) · cloud buckets (new) · public share by IP (new). The add-flow should present a source-kind picker + method, not just “install agent.” build
  2. Object-storage connector — S3 / Azure Blob / GCS as a scan source. build
  3. Scanner-node model — one console-managed on-prem node crawling many internal shares by IP, instead of an agent per server. build
  4. Console-driven agent config. Today agent-hosted targets live in a local JSON file and start by running the exe — the console cannot configure or start them. A console-driven flow needs a config-pull (targets + sealed credentials delivered to the agent on register). build
  5. Network agent polish — MSI installer + enroll key, 24h key expiry, in-wizard drive picker the agent honors, in-agent scheduling, LUKS detection, and the finer “Team only / Owner only” share labels. build
  6. Cloud capability gaps (product call). The design shows data the product does not collect: LIVE/webhooks, link-spread (Slack/Teams/email), link open-counts, apply-policy / response-mode, “Continuous” schedule, granted-scopes list. product decision
  7. Small API adds — no design needed. Error “what to do” guidance text + cause-specific messages, test-before-save (test with inline credentials), repo result-tab counts, Oracle service-name field. in progress
