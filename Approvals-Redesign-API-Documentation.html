What changed

The approvals screens were redesigned around the PolicyV2 override matrix: each policy now says, per severity, whether the user may self-override or must request admin approval, for how long access unlocks, and which role approves ("Medium → Admin approval for 24 hours by DLP Admin; Critical → by QA"). To support this:

AreaChange
GetApprovalList / GetApprovalRequestRows now carry NEW metaId, severity, approverRoles and canApprove (plus the existing policyName). Pass the caller's ?userId= (or portal JWT) to get canApprove per row.
SubmitOverrideRequestNo request-contract change. The server now stores on every request: the activity's severity, and (admin-approval only) the approverRoles allowed to decide it — resolved from the policy matrix at submit time, hierarchy applied.
GetUserOverrideSettingsResponse now includes the full matrix (overrideRules), policySource/policyName, per-route severity lists, and allowCancelWhilePending.
Self Override History tab NEWThree new endpoints: GetSelfOverrideHistory (flat list), GetSelfOverrideHistoryGrouped (View by User / File), and RevokeSelfOverride (admin closes an active window early).
Databasedlp."OverrideRequest" gained Severity and ApproverRoles columns (see deployment note).

All additions are backward compatible — existing fields and shapes are unchanged; old callers simply see the new fields (or null).

Approver hierarchy & CanApprove

A policy's override matrix names approver roles per severity. The hierarchy rule: a role trusted to approve a severity is also trusted with every severity below it (ladder: Critical > High > Medium > Low).

Example — policy says Medium → by DLP Admin and Critical → by QA:
• A Medium request stores approvers DLP Admin, QA (QA covers Critical ≥ Medium).
• A Critical request stores approvers QA only — DLP Admin's rule (Medium) sits below Critical.

The expansion happens once, at submit, and is stored on the request — a later policy edit never silently changes who may decide an already-queued request.

How canApprove is computed per row
Row statecanApprove for the caller
Row has stored approverRolestrue when the caller's role matches a stored token: a digit token is compared to the caller's RoleId; any other token to the caller's role name, ignoring case and spaces (SecurityAdmin matches "Security Admin").
Row has no stored roles (legacy / AppSettings)Falls back to the existing rule: caller is DLP Admin or mapped in PolicyApprovalRoleMap.
Caller not identified (no ?userId=, no JWT)canApprove is null on every row — the flag is omitted rather than guessed.
canApprove is a display flag for enabling/disabling the Approve / Reject actions. Server-side enforcement on the review endpoints is not yet wired — do not treat the flag's absence as a security boundary.

Approvals (admin)

POST/GetApprovalList?userId={callerUserId}UPDATED

Paged, filtered, sorted approval grid. ?userId= names the caller (the admin looking at the screen) so each row can carry canApprove. On the portal the JWT UserId claim is used when the query param is absent.

Request body (unchanged — QueryParameters)

  "pageSize": 15,

  "sortDescending": true,

POST/ReviewOverrideRequest · /BulkApproveRejectUPDATED

The Access Time dialog on Approve: both review endpoints now take grantedDuration + grantedDurationUnit ("Hours" / "Days"). The server validates it against the request's policy time limit — the same number the row's policyTimeLimitMinutes shows — so an approver can shorten a window, never extend it past the policy.

Request body additions
{
  "overrideRequestId": "6f6f3f9a-93f1-4f20-9f3b-2e1f9b7d1c22",
  "reviewedByUserId": 7,
  "reviewedByEmail": "admin@acme.com",
  "status": "APPROVED",
  "reviewComments": "OK for the audit",
  "grantedDuration": 3,            // NEW — the dialog's value…
  "grantedDurationUnit": "Days"    // NEW — …and unit ("Hours" | "Days")
}

BulkApproveReject takes the same two fields once for the batch; each request is validated against its own limit, and one whose policy allows less fails into errors[] instead of silently getting more.

Behaviour
CaseResult
Within the limit200 — access runs grantedDuration from approval (validUntil = validFrom + granted).
Longer than the limit400, errorCode: "LIMIT_EXCEEDED", message: "Policy allows at most 3 days (set in Finance Restrict All). You can shorten it, not extend it."
Fields omittedPre-dialog behaviour, unchanged: the employee's requested duration, then the server default. Old clients keep working.

The limit: the policy matrix rule's unlock duration for the request's severity; the server's AdminApprovalValidityDays ceiling when no rule answers (and for OneUpload rules, which are not time-based).

Self Override History

POST/GetSelfOverrideHistoryNEW

The history tab's flat "All" view. A self-override is auto-approved at submit, so a row's status describes its unlock window, derived at read time: Active while the window is open (with minutes left), Expired once it closes, Revoked when an admin shut it early.

Request body (QueryParameters)
{
  "page": 1,
  "pageSize": 15,
  "status": "Active",                // Active | Expired | Revoked | All (default)
  "fromDate": "2025-09-12T00:00:00Z",
  "toDate": "2025-09-23T23:59:59Z",
  "sortBy": "timesUsed",             // usedOn (default, desc) | userName | fileName | application | timesUsed | validUntil | status | severity
  "sortDescending": true,
  "likeFilters": { "search": "vendor" }   // one box, matches user / code / file / justification / application
}

likeFilters also accepts the specific keys userName, employeeCode, fileName.

POST/RevokeSelfOverrideNEW

Admin revoke of an Active self-override: sets the row to CANCELLED (shown as Revoked by admin), closes the unlock window now (ValidUntil = now, which is what the agent enforces), clears the override flag on the activity, and notifies the admins and the employee through the usual Recent Alerts path.

Request body
{
  "overrideRequestId": "9a1c2e51-70aa-4e0f-8f6e-3d2b1c9e4a07",
  "revokedByUserId": 7,
  "revokedByEmail": "admin@acme.com",
  "comments": "Shared outside the audit scope"     // optional; defaults to "Revoked by admin"
}
Responses
CodeWhen
200Revoked — data.message: "Self override revoked. The unlock window is closed."
400Not a self-override, or its window is already closed (expired / already revoked / pending admin request).
404No such override request.

POST/SubmitOverrideRequestBEHAVIOUR

Request and response contracts are unchanged. What's new is what the server records on the created OverrideRequest row:

Stored fieldWhenValue
Severityevery override (self + admin)The blocked activity's severity at submit time.
ApproverRolesadmin-approval onlyThe matrix's approvers for that severity, hierarchy applied (see above), comma-joined. NULL when no matrix answered — the DLP Admin fallback decides, exactly as before.

AI-prompt overrides (SubmitPromptOverrideRequest) store neither — prompts carry no severity, and their approval stays on the DLP Admin fallback.

Deployment note (SQL)

Before these fields return data on an environment, run SFM.DLP.Infrastructure/Data/Migrations/AddSeverityApproverRolesToOverrideRequest.sql against each client's DLP database. It is guarded and re-runnable: adds dlp."OverrideRequest"."Severity" (varchar 20) and "ApproverRoles" (varchar 500), and backfills Severity from crunch."LandingLogsCrunched". ApproverRoles is deliberately not backfilled — NULL already means "DLP Admin fallback", which is how legacy rows were always handled.

Until the SQL runs, the API will error on these endpoints (EF selects the new columns). Deploy SQL first, then the API.
