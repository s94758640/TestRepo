What this is

Connect a Git host — Azure Repos, GitHub, GitLab or Bitbucket — and the crawler reads every repository it can see, scans the files for committed credentials, and records what it finds with the path and line. The console shows two grids: Repositories (what is connected and what each holds) and Findings (one row per credential).

A code connector is created, tested, scanned and cancelled through the same endpoints as a cloud storage connector. Only the results live elsewhere. That split is the single most important thing on this page — see below.

Credential values are never stored. A finding carries a maskedValue, the rule that matched, and the path and line. The secret itself is not persisted anywhere.

Code vs cloud storage — what is shared, what is not

One connector table and one scan queue serve both. Nothing below them is shared.

Cloud storage (OneDrive, SharePoint, Box…)Code repositories (Azure Repos, GitHub…)
Create / testcloud/connectors, cloud/connectors/test — same for both
Start / cancel a scancloud/scans, cloud/scans/cancel — same for both
Connector kindCloudStorageCode
Results live incloud/containers, cloud/filescode/repositories, code/findings
Unit of scopecontainer (drive, site, library)repository
Incremental cursordelta token per containerlast scanned commit (HEAD SHA) per repository
Do not judge a code connector from the cloud grid. On cloud/connectors, a code connector permanently reports containerCount: 0, fileCount: 0, sensitiveFiles: 0 and totalSize: "0 Bytes" — those count cloud containers and cloud files, which a repository never becomes. A connector scanning forty repositories still shows zeroes there. Read code/repositories and code/findings instead.

Conventions & headers

HeaderRequiredNotes
ClientGUIDrequiredTenant identifier — routes to the correct tenant database.
AuthorizationrequiredBearer <jwt>. Every endpoint on this page needs a token.
Content-Typerequiredapplication/json.
Envelope. Every response is { "success", "message", "data", "errors" }. The samples below show the data contents only.
Casing. Responses are camelCase. Grid filter keys inside exactFilters / likeFilters are column names and keep their PascalCase spelling.
Dates. ISO-8601 UTC on the wire.

Connecting a Git host

1GET/cloud/providers

Every provider the wizard can offer, with the field labels that provider's own console uses. Filter to the code ones by kind: "Code".

ProviderTenant field is calledAuth method recorded
AzureReposOrganisationAppKey
GitHubOrganisationAppKey
GitLabGroupAppKey
BitbucketWorkspaceAppKey

Use the labels from this response in the form. "Organisation" for Azure Repos and "Workspace" for Bitbucket are the words the admin is reading off the other screen; externalTenantId means nothing to them.

2POST/cloud/connectors

Creates the connector. Same endpoint and same body as a cloud storage connector; the provider decides the rest.

{
  "provider": "AzureRepos",
  "displayName": "Defensely repos",
  "externalTenantId": "ManageEndPoints",
  "clientId": "8b0513cd-f620-4394-9e59-49fa95ac557e",
  "clientSecret": "<service principal secret or PAT>",
  "credentials": { "project": "Defensely" }
}

The connector is created with status: "Pending" and authMethod: "AppKey". It is not usable until it has been tested or has completed a scan.

One connector per account. Creating a second connector for a provider account that is already connected returns 400 naming the existing one. Update that connector's credentials, or remove it first — re-running the wizard after a rejected credential used to leave a duplicate behind each time.
3POST/cloud/connectors/test

Proves the credential and reports the scope it can see. Run it before the first scan.

{ "cloudConnectorId": 7 }
Response — data
{
  "success": true,
  "error": null,
  "containers": [
    { "name": "Defensely / Defensely-WebAPI",  "cloudContainerId": 0, "externalId": "" },
    { "name": "Defensely / Defensely-WebSite", "cloudContainerId": 0, "externalId": "" }
  ]
}
cloudContainerId: 0 and an empty externalId are correct here, not a half-finished connection. The scope is reported through the same containers field the storage providers use so the wizard needs no second shape; a repository gets no id on our side until the first crawl writes one. Render name — it carries project / repo.

On success the connector moves to Connected and lastValidatedAt is stamped. On failure it moves to Failed with the reason in lastError, and data.error carries the same text — show it as-is, it names what to fix at the provider.

Scanning

4POST/cloud/scans

Queues a crawl. A worker picks it up on its next poll — this returns as soon as the job is queued, it does not wait for the scan.

{ "cloudConnectorId": 7, "scanType": "Full" }
scanTypeDoesUse when
FullForgets every repository's last scanned commit and reads them all again.First run, after changing rules, or when you want a clean re-read.
IncrementalSkips any repository whose HEAD has not moved since its last successful scan.Routine and scheduled runs. This is what makes a daily scan across hundreds of repositories affordable.
An Incremental scan finishing in seconds with filesSeen: 0 is correct when nothing has been committed since the last run. Every repository took the skip. If a Full scan does that, something is wrong — tell the API team.
One active scan per connector. Queueing while one is already Queued, Running or Cancelling returns 400 naming the job. Cancel it first. A job whose worker has died does not block a new one.
5POST/cloud/scans/list

Scan history and live progress. cloud/connectors also carries the latest job per connector, which is what the grid's status chip reads.

The fields that matter on a code scan
FieldMeans
statusQueuedRunningCancellingStalledCompletedFailedCancelledStopped
startedAtNull means no worker has claimed it yet. The first thing to check when a scan "does nothing".
filesSeenFiles read across all repositories. Moves during the crawl.
filesExtractedRepositories scanned — not files. The column means something different here than on a cloud scan.
filesFailedRepositories that could not be scanned. Check this even when the status is Completed.
lastHeartbeatAtLast sign of life. A Running job with a stale heartbeat is reported as Stalled.
Completed alone is not success. A scan reports Completed even when every repository failed — the failures are counted in filesFailed and the crawl continues past them on purpose, so one unreadable repository cannot end a scan of three hundred. Treat Completed with filesFailed > 0 as a partial result and read lastError on the affected rows in the repositories grid.
6POST/cloud/scans/cancel

Asks a scan to stop.

{ "cloudScanJobId": 66 }
Job wasBecomesWhy
QueuedCancelled immediatelyNever started; no worker to notify.
Running, worker aliveCancelling, then CancelledThe worker stops at its next batch boundary, where everything is saved.
Running, worker goneCancelled immediatelyNobody is listening, so there is nothing to wait for.
Already finishedunchangedThe caller wanted it stopped, and it is.
Cancelling still counts as scanning — isScanning stays true until it settles. Show it as a distinct state rather than as "Running", so a user who pressed Cancel can see that it registered.

Results

POST/code/repositories

The Repositories grid — what is connected and what each holds. Standard grid contract: page, pageSize, sortBy, sortDescending, exactFilters, likeFilters.

Sort and filter on the row's own fields: Name, Provider, Visibility, FindingCount, CriticalCount, LastScanAt.

{ "page": 1, "pageSize": 25, "sortBy": "FindingCount", "sortDescending": true }
Response — data
{
  "totalCount": 42,
  "data": [
    {
      "codeRepositoryId": 118,
      "cloudConnectorId": 7,
      "provider": "AzureRepos",
      "name": "Defensely-WebAPI",
      "namespace": "Defensely",
      "webUrl": "https://dev.azure.com/…/_git/Defensely-WebAPI",
      "visibility": "Private",
      "defaultBranch": "main",
      "findingCount": 12,
      "criticalCount": 2,
      "filesScanned": 1877,
      "lastScanAt": "2026-11-04T02:41:03Z",
      "lastAttemptAt": "2026-11-04T02:41:03Z",
      "isScanned": true,
      "scanFailed": false,
      "lastError": null,
      "isExcluded": false,
      "isDeleted": false
    }
  ]
}
Three states, not two. isScanned: false means never reached. scanFailed: true with lastError means it was tried and could not be read. isScanned: true with findingCount: 0 means scanned and clean. The grid must not show the first two as a clean result — "no findings" and "no answer" are opposite things.

isDeleted marks a repository that is gone at the provider. It is kept because its findings outlive it.

GET/code/rules

The scanner's rule catalog — what it looks for. Feeds the findings grid's Rule filter, and gives ruleName on a finding somewhere to be explained from.

Response — data
[
  { "ruleId": "private-key",             "name": "Private key block",                "confidence": 99, "severity": "Critical" },
  { "ruleId": "aws-access-key",          "name": "AWS access key id",                "confidence": 95, "severity": "Critical" },
  { "ruleId": "azure-storage-key",       "name": "Azure storage connection string",  "confidence": 95, "severity": "Critical" },
  { "ruleId": "github-token",            "name": "GitHub token",                     "confidence": 95, "severity": "Critical" },
  { "ruleId": "stripe-key",              "name": "Stripe secret key",                "confidence": 95, "severity": "Critical" },
  { "ruleId": "slack-token",             "name": "Slack token",                      "confidence": 90, "severity": "High"     },
  { "ruleId": "db-connection-password",  "name": "Password in a connection string",  "confidence": 55, "severity": "High"     },
  { "ruleId": "google-api-key",          "name": "Google API key — check its restrictions", "confidence": 90, "severity": "Medium" },
  { "ruleId": "jwt",                     "name": "JSON web token",                   "confidence": 60, "severity": "Medium"   },
  { "ruleId": "generic-assigned-secret", "name": "Secret assigned to a variable",    "confidence": 40, "severity": "Medium"   }
]

Worst first, then most confident — a legend reads top-down. Pass ruleId values back in code/findings's ruleIds.

Severity here is the floor, not the value on the row. It is the rule's severity before the repository's visibility is considered: the same key found in a public repository is reported at a higher severity on the finding itself. A legend built from this list will not always match the chips in the grid, and that is correct.
The default minConfidence: 50 hides exactly one rule — generic-assigned-secret at 40. Everything else is above the line. Lower the threshold to see it; it catches real leaks and most of the noise.
The matching pattern is deliberately not returned. It is detection logic, and publishing it tells anyone who can open the console precisely what the scanner does and does not catch. No database is touched by this call — the list is the same one the crawl runs.

isPresent: false does not mean fixed, and the UI must not say it does. It means the line is gone from HEAD. The secret is still in git history and the key is still live until somebody rotates it. These are the findings most often wrongly believed closed, which is why they are included by default — label them something like "removed from code, not rotated", never "resolved".

ageDays is from firstSeenAt, and it is the number that matters in an incident: a key exposed for eight months is a different conversation from one exposed this morning.

sourceUrl is a deep link to the line at the provider, or null when the repository URL is unknown. Hide the action rather than offering a link that goes nowhere.

GET/code/findings/summary

The tiles above the findings grid. Describes the whole population, not the current page. Optional ?cloudConnectorId=7 narrows it.

{
  "totalFindings": 184,
  "critical": 12,
  "high": 41,
  "medium": 88,
  "low": 43,
  "inPublicRepositories": 7,
  "removedButNotRotated": 23,
  "repositoriesScanned": 42,
  "repositoriesWithFindings": 19
}
TileWhat it counts
inPublicRepositoriesFindings in repositories anyone on the internet can read. The tile to act on today.
removedButNotRotatedNo longer at HEAD but never resolved — somebody deleted the line and moved on. The key is still live.
repositoriesScanned / repositoriesWithFindingsCoverage, so "12 criticals" can be read against how much was actually looked at.
POST/code/findings/resolve

Records that a person dealt with a finding. Only a person can do this — a scan can see whether the line is still there, which is a different question.

{ "repoFindingId": 9041, "reason": "Key rotated in AWS and the old one revoked." }
FieldTypeNotes
repoFindingIdlongrequired—
reasonstringrequiredRejected with 400 if blank.

Returns the updated finding row. The caller is recorded from the token in resolvedBy, with resolvedAt.

The reason is required on purpose. The three outcomes — rotated, false positive, risk accepted — need telling apart afterwards, and that is the first question in any incident review. A resolution with no reason is a row nobody can audit. Offer the three as presets in the UI rather than a free-text box alone.

States & vocabulary

Connector status
PendingCreated, never proven. Neither a test nor a completed scan has succeeded yet.
ConnectedA test or a completed crawl has proven the credential.
FailedThe last test failed; lastError says why.
DisabledRemoved by an admin. Soft delete — the findings already discovered stay queryable.
Finding severity

Derived from the rule and the repository's visibility, so the same leaked key is a worse problem in a public repository than a private one. A repository made public turns every finding in it into a higher severity on the next scan.

Gotchas

You seeIt means
Connector shows 0 containers, 0 files on cloud/connectorsNormal for a code connector. Those count cloud containers and files. Read code/repositories.
Scan Completed in seconds, filesSeen: 0Incremental scan, nothing committed since the last run — every repository took the skip. Expected. Run a Full scan to force a re-read.
Scan Completed but no findings appearedCheck filesFailed. A scan completes even when every repository failed.
Scan sits at Queued, startedAt nullNo worker has claimed it. The crawl runs in a separate service from the API.
Running but nothing movingCompare filesSeen a minute apart. Frozen means it is heading for Stalled.
Test succeeds but connector still PendingShould not happen — report it. A successful test writes Connected and lastValidatedAt.
filesExtracted looks far too smallIt counts repositories, not files, on a code scan. filesSeen is the file count.
