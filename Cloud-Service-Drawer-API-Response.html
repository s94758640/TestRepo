Shipped

authMethod is recorded on save rather than inferred from which credential column is filled — an inferred answer changes when a secret is rotated, and "how was this authorised" must not.

Not shipped, and not API-side

  • authorizedBy — nothing captures who gave consent. No person is recorded anywhere on a connector. It has to be captured at the consent step, which is the setup wizard.
  • grantedScopes — we never ask the provider what it actually granted; we find out when a call fails. Reading the real grant is a change to connector validation, and it will not be uniform across providers.

Your reason for wanting the scopes — "we can show it before a scan fails" — is a good one and we want it too. But it is connector-validation work, not drawer work. Please build the Connection tab to work without those two.

Your shape, unchanged. Two things worth knowing:

  • newFiles and sensitiveFound are not stored on the job — they are derived from when each object was first recorded. A crawl still in progress therefore reports what is new so far, not zero.
  • status is the effective status. A crawl whose worker died reads Stalled rather than Running forever, so this list cannot contradict the Scan button next to it.

The 404s you hit were real: /cloud/scans and /cloud/connectors/{id}/activity do not exist and were never routes.

Where it sits — share % and main class

Done

POST /cloud/containers

"sharedBeyondOwnerPct": 38.4,        // number, 0–100, one decimal
"topClassification":    "PHI"        // null when nothing sensitive here

Same type as /cloud/locations, not just the same meaning. We first made this an integer, which would have had one field name arriving as an int on one endpoint and a decimal on the other — one client, two types. It is a decimal with one place on both.

The percentage is over the location's sensitive files, matching /cloud/locations. topClassification breaks ties by name, so the tag does not flip between reads of unchanged data.

The filter bug was two bugs. Both fixed.

The location row carried no connector. Only a provider — which is why two connectors on one provider could not be told apart, exactly as you found. Rows now carry cloudConnectorId, so exactFilters.cloudConnectorId: ["2"] works.

The unknown key was swallowed. The shared filter helper catches per-key failures and carries on, so your filtered request returned every row with a 200 — a filter that did nothing and said nothing. Keys are validated before they are applied now.

Please re-test your existing cloud grid calls.

A consequence of that second fix: cloud grids now answer 400 with the offending key named where they previously returned everything. That is the point — but if any current call sends a key that does not exist on the row, it will start failing where it used to silently succeed. Better to find that now than later.

POST /cloud/files

Confirmed out, per your reply. For the record: cloud files are classified by pattern matching only. There is no AI path for cloud content and nothing records which engine produced a finding, so the chip would read "Regex" on every row forever.

Your own probe said it best — Bad6.txt returning PCI_CARD_NUMBER and PII_PAN is exactly what the pattern scanner emits, because it is the only thing that ran.

Making it real is crawl work in two parts: recording the engine per finding, and deciding whether cloud files should be AI-classified at all.
