DLP Dashboard — Data Gap Analysis

The client's dashboard design, checked against the data we actually hold · for the product & delivery team

What this is

The client gave us a finished dashboard design as a working HTML prototype. It is their design and it is not being changed.

This document answers one question only: for each thing that design shows, do we have the data? So we can tell the client what is not achievable before anyone starts building it.

❌ The seven we cannot build

These are the conversation to have with the client. The last two are in the pop-out detail panel rather than on a tile.

1. Violations by Regulation

The regulations themselves already exist in our system — DPDP Act, GDPR, SOX, PCI DSS, HIPAA, Source Code and Credentials are all policy templates with a severity against each.

What is missing is the link from an event to a regulation. When we record a blocked file transfer we save only the policy name, as free text. We do not save the policy id. Policy names can be renamed by an admin at any time, so matching on the text is unreliable — we cannot say with confidence which regulation a given violation belongs to.

To make it possible: record the policy id on each event going forward. This is the single most valuable change for this dashboard — it unlocks the whole widget.

2. Insider Risk Signals — “Departing Employee”

This one needs to know an employee has resigned. We hold no such information: a user is only ever active or disabled. There is no resignation date, no last working day, no notice period, and no HR system integration anywhere in the product.

Worth showing the client: their own prototype fakes it — the code contains a hardcoded list of two user ids rather than a real signal.

To make it possible: an HR system feed. A significant piece of work in its own right, not part of a dashboard.
The other three insider signals are fine — see the amber list.

3. Warnings Bypassed

On the Web Filtering tab this shows how often a user was warned and carried on anyway. We record that a warning was shown. Nothing records that the user then proceeded — and the agent does not send that information at all.

To make it possible: an agent change to report the outcome of a warning, plus somewhere to store it. Needs the agent team.

4. Top External Devices — as individual devices

The design lists specific devices (“SanDisk Ultra 64GB”, “Kingston DataTraveler”). We only know the device type — USB, Bluetooth, NAS, RDP. No serial number, no manufacturer, no volume label. The serial number we do store belongs to the laptop, not to the USB stick plugged into it.

Possible today: “Top device types”. Not possible: naming individual devices, without an agent change.

5. Endpoint Coverage — the “Warning” slice

The donut shows Healthy / Offline / Warning. We only ever record an endpoint as Online, Offline or Locked. There is no third state, and the code carries a note that this bucket was deliberately removed once before.

Closest thing we do have: an endpoint that is online but whose DLP service is not running. If the client agrees that is what “Warning” means, it is buildable.

6. “Characters” on a Content event

When you click a Copy/Paste or Typed Content event, the detail panel shows a character count. We do not store one — there is no such field anywhere.

Partly possible: we could count the captured text where we hold it. But when a customer has sensitive-content masking switched on we do not keep the text, so the count would be missing for exactly the events that matter most. Best confirmed with the client whether it is needed.

7. “Mark as reviewed” — on web and AI prompt events

Every detail panel in the design offers a Mark as reviewed action. We have a review status, but only on file-transfer events. AI prompt events and web requests have no such field, so the button would do nothing on two of the four tabs.

To make it possible: add the same review status to the prompt and web-filtering records. Small change, but it must be done or the action has to be hidden on those tabs.

The full click list — and what we found in it

The design has 62 clickable targets. Checking all of them, rather than the ones visible in the screenshots, turned up widget groups we had not seen — Custom Word & Regex Matches, Lists & Exceptions, Large File Rule, Top Policies Triggered, and the Recent Events lists — plus drill-downs for video recordings, shadow file copies, override requests and large files.

The good news: almost all of the newly-found ones are things we already hold — video recordings, shadow copies, override requests, regex and custom-word matches, large-file handling, allow/block lists and policy exceptions. No new gaps came out of them.

But several predicates in the prototype are placeholders

Reading the prototype's own code, a number of tiles are not computing anything real — they use a hash of the record id to produce a plausible-looking spread. This matters because it tells us what the client has specified versus what they have merely sketched.

TileWhat the prototype actually doesWhat we would really use
False positives / negatives reported A hash of the event id, split by whether it was allowed Our Feedback module — False positive and False negative are two of its seven feedback types. Real data, and newer than this design.
Shadow file copies — “Licensed users only” licensed = userId % 10 < 7 — arithmetic on the id Real shadow-copy records and real licence assignment.
Override requests Blocked events, filtered by the same hash dlp."OverrideRequest" — actual requests, with status, justification and validity window.
Video recordings Critical severity and not allowed The real video flags on the event, which say whether a recording exists.

In each case our data is better than the prototype's stand-in. Worth confirming with the client that these tiles should use the real source, because the numbers will not match their mock-up — and that is the correct outcome.

The design contradicts itself on off-hours. The Off-Hour Activity tile is captioned “Before 07:00 or after 21:00”, while the After-Hours Transfer insider signal on the same screen says “Outside 08–20 local time”. Two different definitions of the same idea, on one dashboard. We also store a third — each customer's real business hours, defaulting to 09:30–18:30. The client needs to pick one, and our recommendation is their own configured business hours.

What needs the EXE / agent team

Three of the seven gaps cannot be closed from the server at all — the agent does not capture or send the information today. These are a separate piece of planning, to be agreed with the agent team before any of them is committed to the client.

Four problems we will hit on the way

These are existing faults the new dashboard will put on screen. Worth raising now rather than discovering them in testing.

  1. Off-hour activity is currently calculated wrongly. The code assumes 9am–6pm UTC and ignores the business hours we already store for each customer (default 09:30–18:30 India time). For an Indian customer this is out by five and a half hours and wrongly labels most of the normal working day as out-of-hours. The business end time we store is currently read by nothing at all.
  2. “Total Active Policies 24/26” would show the wrong number. The current code counts how many distinct policy names appear in the logs, not how many policies are actually active.
  3. Three different risk scales are in use and they disagree with each other. The new Overview puts the organisation score and the per-user risk bands on the same screen, so they will visibly contradict unless we settle on one.
  4. The dashboard will be slow. Almost every existing tile loads full event records into memory and adds them up in code rather than in the database. There is an unused table in our schema whose columns read like a specification for exactly this dashboard — it is either the answer or it should be deleted.

These four queries settle every amber item above.

SELECT DISTINCT "AiProvider"        FROM dlp."AIPromptLog";
SELECT "BusinessStartTime","BusinessEndTime","TimeZone" FROM sfm."Client";

SELECT DISTINCT jsonb_array_elements_text(
         ("FileContent"::jsonb -> 'classificationSummary' -> 'DlpType'))
  FROM crunch."LandingLogsCrunched"
 WHERE "FileContent" IS NOT NULL
 LIMIT 100;

They answer, in order: do we really capture Device Read/Write and Copy-Paste; does DeepSeek appear; are business hours set correctly; and does the scanner actually produce PCI, Credentials and Customer Data.
