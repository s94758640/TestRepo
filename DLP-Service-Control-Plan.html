1. The moving parts

PieceWhat it isOwner

Which machines this covers

Windows endpoints running both DLPService and iseccmd. The endpoint is identified on the wire by its serial, which we verified against QA — see §13, because it is not always the BIOS serial.

2. End-to-end flow

0.  iseccmd boots
    → wss://{BaseUrl}/ws/endpoint-commands?serial=PW0F6X3B   (ClientGUID header)
    → we validate, register serial → socket, replay any open commands
    → socket stays open: agent pings every 30 s, we MUST answer pong

1.  Admin clicks Stop
    → POST /api/endpoints/{serial}/service-command   { action:"Stop", persist:true }

2.  we supersede any open command for that serial, insert the new one as Pending

3.  socket is up → push  {"type":"ServiceCommand", commandId, action, persist}
    → state Delivered
    → 202 { commandId, state:"Delivered", endpointConnected:true }

4.  agent → ServiceCommandAck            (sent before it runs)   → state Acked

5.  agent → Service Control Manager: stop DLPService
                                     set start type Disabled      (persist only)

6.  agent → ServiceCommandResult { success, finalStatus, startType, elapsedMs, message }
    → state Succeeded or Failed, CompletedAt stamped

7.  console polls GET /api/service-commands/{commandId} every 1 s until the state is final
The budget 10 seconds from click to result. The agent's own sample reports elapsedMs: 2310 for a Stop, so the transport has roughly 7 seconds of headroom.

The four deviations

SituationWhat happens
Endpoint offline at click Row stays Pending; the 202 returns endpointConnected:false. On the agent's next connect we push every open command, oldest first. Stop and Start never expire — they are the state the admin wants, still true an hour later. A Restart older than 10 minutes becomes Expired and is not run: it was about a moment that has passed.
Second click while one is open The new command supersedes the old. At most one open command per endpoint. Offline Stop then Start means only the Start runs.
Socket drops mid-execution The agent posts the result to /ReportServiceCommandResult instead. Same state transition, matched on commandId.
Same command pushed twice The agent does not re-run it — it replays the stored result, or re-acks if still executing. This is what makes replay-on-connect unconditionally safe.

3. UI — what the console does

Three calls, one of them on a timer. The console never contacts the endpoint.

MomentCallWhat the UI shows
Screen loadsGET /api/endpoints/{serial}/push-status Online / offline beside the toggle, before the admin clicks
Admin clicksPOST /api/endpoints/{serial}/service-command Toggle goes to a pending look; disable it until the command is final
Every 1 s afterGET /api/service-commands/{commandId} Poll until state is final, for up to about 60 s

States the UI has to render

ResponseMeaningShow
state:"Delivered", endpointConnected:true On its waySpinner on the toggle
state:"Pending", endpointConnected:false Saved, endpoint offline Not an error. "Will apply when the endpoint comes online" — and stop polling early, it may be hours
state:"Succeeded"Done Toggle to the new position; finalStatus / startType are what the machine reported
state:"Failed"The machine refused or timed out Revert the toggle and show message — it is the agent's own text
state:"Superseded"The admin clicked again Drop this one silently; the newer command owns the toggle
state:"Expired"A stale Restart, never run "The endpoint came back too late — restart again if you still need it"
The "off" toggle means persist:true persist applies to Stop only. True also sets the service start type to Disabled, so it stays off across a reboot — which is what an admin means by turning DLP off. Send false for a one-time stop that comes back on reboot. Ignored for Start and Restart.
Stop polling on a final state, and cap it Final means Succeeded, Failed, Superseded or Expired. A command that is still Pending after ~60 s is waiting on an offline endpoint; keep the row in its "will apply later" look rather than polling for hours.

6. Data model and states

dlp."ServiceCommand", one row per click. Per tenant, like every table in dlp — migration V0054__service_command.sql must run against every tenant database, not only the template.

Pending→Delivered→Acked→ SucceededFailed  also SupersededExpired
StateSet when
PendingCreated while offline, or the send failed
DeliveredWritten to the socket
AckedServiceCommandAck received
Succeeded / FailedServiceCommandResult, by its success
SupersededA newer command was created for the same serial
ExpiredA Restart that reconnected more than 10 minutes late

Open = Pending, Delivered, Acked. Only open rows are replayed and only open rows change state on a result. Result fields are stored on every row that receives one, including Superseded and Failed — a Stop that failed because the service was already stopped reads very differently from one that timed out.

One addition to the spec, database-level only Rule 1 — "at most one open command per endpoint" — is enforced by a partial unique index as well as in code. Two admins clicking in the same instant is exactly what the service layer cannot serialise on its own, and the failure is otherwise silent: two open rows, both replayed, the agent running whichever lands last. 
CREATE UNIQUE INDEX "UX_ServiceCommand_OneOpenPerSerial"
    ON dlp."ServiceCommand" ("Serial")
    WHERE "State" IN ('Pending','Delivered','Acked');
No protocol change. The second insert fails loudly and the caller retries after superseding.

7. Delivery across replicas

The problem the spec treats as optional, and we cannot §9 says "a single instance needs neither". We run multiple replicas on Container Apps, with no request affinity: 
admin clicks  →  POST lands on replica A   (holds no socket)
agent socket  →  held by replica B   (never hears about it)
With 2 replicas that is a 50% failure rate, with 3 it is 67% — and low admin volume does not help. Each click is an independent coin flip, and the failure is silent: the row sits Pending until the socket next drops.

How we solve it — the socket holder polls the table

Replica B holds sockets for serials [X, Y, Z]

every ~2 s:  SELECT * FROM dlp."ServiceCommand"
             WHERE "State" = 'Pending' AND "Serial" = ANY(@serialsIHold)
             → push each, mark Delivered
Why not Service Bus or Redis
Latency2 s worst case + ~2.3 s execution, inside a 10 s budget
InfrastructureNone added. No topic, subscription or new service
Failure handlingSelf-healing — a missed push retries next tick. No delivery guarantees, dead-lettering or ordering to reason about
Code pathsOne. This is the same query replay-on-connect already needs, so offline-reconnect and wrong-replica share it
Cost at rest3 replicas × one indexed query every 2 s, on IX_ServiceCommand_Open_CreatedAt

Service Bus buys sub-second instead of up-to-2-second delivery. The budget is 10 seconds, so it is not worth the dependency. It stays the upgrade path if measurement ever says otherwise.

8. Why raw WebSocket, not SignalR

Settled deliberately, because it is expensive to change after the agent ships against it. Neither SignalR nor Web PubSub is referenced anywhere in the solution today.

Client protocolFits this agent?
Azure SignalR Service SignalR only — HTTP negotiate, handshake frame,  separators, integer type inside an envelope No the agent sends {"type":"ping"} bare
Azure Web PubSubRaw WebSocket, arbitrary frames Protocol yes but its own hostname and an access token, so the agent's connect URL and flow change
Self-hostedRaw WebSocket Yes, unchanged

SignalR is out on protocol grounds whatever is provisioned — adopting it means the EXE team rewriting and re-testing the endpoint half that is already finished. Web PubSub keeps the protocol but moves the hostname, which is also an agent change, to buy capacity and metrics we do not need at one idle socket per endpoint and two frames a minute.

We are not blind without a managed service dlp."ServiceCommand" records the whole lifecycle — CreatedAt → DeliveredAt → AckedAt → CompletedAt → ElapsedMs. "How long from click to result", "how many never acked", "which endpoints never deliver" are SQL questions. That answers does the feature work better than a connection count does.

Triggers to revisit: connection count outgrowing a replica (measure before a third feature moves onto the socket), or deploy churn becoming painful — every revision drops every socket at once and all agents reconnect together.

13. Open items

The serial is not always a BIOS serial — this is the one real question Checked against QA: 68 endpoint rows, 49 distinct serials, none shared between machines, no nulls or empties, all uppercase. So serial is a safe identity and one-socket-per-serial holds. Compare case-insensitively and trimmed.

But the column holds two shapes: real service tags (PW0F6X3B, 5CD2026Q39, F0WJNQ2) and a 32-char dashed fallback (1415-6109-6884-2945-9939-7533-26, one of them zeroed 0000-0000-…) written when the BIOS reports nothing usable. Lengths run 7 to 57.

Does iseccmd derive the serial the same way the registering agent did, including that fallback? If it only reads the BIOS, every machine stored with a dashed id fails the upgrade and shows as permanently offline, with nothing on screen to explain it. One machine from each group settles it.

14. Future — moving the polled endpoints onto this socket

Service control is the first user of this transport, and it will not be the only one — but nor will it be many. Four or five polled endpoints move onto the socket at most, ever; everything else keeps polling. Nothing in the protocol needs to change to add them: type is a string and both sides ignore what they do not know, so new message types are additive and an old agent simply ignores them.

That bound is a design input, not a caveat No message bus, no envelope, no routing layer — four or five type values on a flat protocol is the right size, and a managed transport (§8) stays off the table permanently rather than deferred. It also means the socket never quietly becomes load-bearing for half the product, which is the failure mode worth avoiding.

Two free decisions to take now

Keep the registry and the delivery poll generic — "send this frame to this serial", not "send this ServiceCommand". Service control becomes one caller of a transport rather than being the transport. Costs nothing today; retrofitting means reopening the socket handler.

The rule that makes migration safe: push the notification, not the payload

us    → agent   {"type":"PolicyChanged","endpointUserId":4821}
agent → us      GET V2/PolicySnapshot/4821        ← the existing route, unchanged

Because the frame cap is 64 KB and a policy snapshot will exceed it; because the HTTP route stays the source of truth so cold start and socket-down need no second code path; and because ordering, retry and chunking stay off the socket entirely.

Never remove a poll — lengthen it Every migrated endpoint keeps its poll as a slow safety net, say 15 minutes instead of 30 seconds. Push becomes the fast path, polling the floor. An endpoint that works only over the socket turns every socket outage into a correctness bug rather than a latency one.

Candidates, best first

Polled todayWhy
CheckOverrideStatus, CheckPromptOverrideStatus, CheckMetaStatus A user is blocked at their screen waiting for an admin decision while the agent polls. The strongest case in the list
V2/PolicyCheck + V2/PolicySnapshot PolicyCheck already is "has it changed?" — exactly the question a push answers
GetDiscoveryScanJobScans would start on click
GetEndpointExeSettings, GetAgentProxyExclusions Config applies immediately instead of on a timer
GetAlertMessagesByEndpointUserMessages shown when sent
GetEndPointCommand The existing pull command channel. Do this last, if at all — it has a real contract and is the least painful poll of the set

Not candidates: everything the agent writes (InsertLandLog, UpdateEndpointStatus, Submit*, Upsert*) and the Download* routes — already request/response with no waiting.

Sequencing, and what would make it a bad idea

  1. Ship service control and prove the socket in production.
  2. Then one migration — override status, highest value and lowest risk.
  3. Measure before the third. Sockets per replica, memory, reconnect storms after a deploy.

One socket carrying everything concentrates failure: today a flaky socket costs service control, after four migrations it costs approvals, policy delivery and scans at once. The lengthened polls are what keep that a latency problem rather than an outage. And every migration is EXE-team work too — which is why user-visible waits lead and config refresh trails.
