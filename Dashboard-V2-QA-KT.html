Read this first

  1. Four tabs, thirteen endpoints, one screen. Overview, File Sharing, Content Sharing and Web Filtering are four views over the same event store. Every endpoint is a POST under /dashboard/v2 and every one of them takes the same JSON body — a filter. There are no query strings and no path parameters to vary.
  2. Nothing is cached and nothing is precomputed — except the Organization Risk Score, which is the one number on the page this API does not calculate. Every other figure is counted from the log tables at the moment you ask. The numbers move while you test. A screenshot of the Overview taken at 14:02 and one of the File Sharing tab taken at 14:04 will not match, and that is not a bug. When comparing two tabs, reload both within the same minute, or compare the raw API responses rather than the screens.
  3. Three populations, three different tables. File, Content and Web are not slices of one list — see the next section. Most "the numbers don't add up" reports trace back to this.
  4. Every click opens the same endpoint. Tiles, bars, donut segments, legend rows, table rows and heat-map cells all call drill-down. They differ only by the filter the UI sends. So a panel showing the wrong events is almost always the wrong filter being sent, not a wrong query — ask for the request body before raising it.
  5. Always capture the request body. In DevTools → Network, click the call → Payload. A dashboard defect without the request body cannot be triaged, because the body is the entire question that was asked.

The three populations — the one concept to take away

Everything on this screen belongs to exactly one of three groups, and they come from different places in the database.

AreaChannels in itRead fromCarries
file UploadDownloadDevice WriteDevice Read crunched transfer logs, via the combined activity view file name, size, severity, destination app, device
content Copy / PasteTyped ContentPrompt crunched transfer logs + AI prompt logs, via the same view detected data types, AI tool, outcome. No severity, no file size
web — none — a separate table, WebFilteringLog domain, category, verdict. No severity, no channel, no scanned content
Three consequences QA will hit on day one.
  • Content events have no severity. So the Content Sharing tab's Risk by Channel severity bar is entirely "Not assessed" grey, and filtering content by Critical returns nothing. Correct, not empty-by-accident.
  • Web requests have no severity, channel, data type, device or size. Sending any of those filters with "areas":["web"] returns an empty panel on purpose — the endpoint skips the web read rather than returning rows that do not satisfy what was asked.
  • A USB write is stored as an Upload with a device flag, not as its own transfer type. The dashboard splits them back out. If Device Write ever reads 0 while the Top Device Types card lists thousands of events, that split has regressed — that is a defect.
"Web Filtering" here is not the Logs screen's "Web Filtering". The Logs screen has an activity group with that name which contains file transfers made through a browser. This tab reads the web-request log — URLs a policy matched. The two are different populations and are not expected to produce the same totals. A mismatch between this tab and the Logs screen is not a defect by itself.

Dates, time zone and the ↑/↓ badges

RuleWhat it means when testing
The window is half-open — fromDate inclusive, toDate exclusive An event at exactly toDate is in the next window, not this one.
A bare date as toDate means the whole of that day "toDate":"2026-11-17" covers up to 2026-11-18 00:00. Picking 11-11 → 11-17 in the picker includes all of the 17th.
Off-hours and the heat map are in the tenant's time zone The response echoes timeZone and businessHours — on QA, Asia/Kolkata and 09:30–18:30. Check the echo before disputing an hour. Event timestamps elsewhere in the API are UTC.
A badge compares against the immediately preceding window of equal length A 7-day window is compared with the 7 days before it. Change the range and every badge legitimately changes.
null badge means "render nothing" Not 0%, not 100%. It means the previous window had nothing to compare with, or no dates were sent. A badge reading "↑ 100%" on a brand-new metric would be the defect.
No date at all = no window All history. Every badge will be null, correctly.

Overview tab — where each number comes from

On screenWhat it countsWatch for
Organization Risk Score + the five bars Averaged from the daily risk snapshots written by the scoring pipeline — the only figure on this page this API does not compute. Mean per user first, then across users, so a user who reported on 30 days does not outweigh one who reported on 3. If the pipeline has not run for the window, the response is riskLevel:"Unknown", scoredUsers:0. The UI must say unavailable — a reassuring "0" over missing data is a defect.
Total Incidents Blocked + Warned + Override across all three areas. It is not the sum of the three area cards — those show all events including Allowed. Do not raise that as a mismatch.
High-Risk Users Distinct users with at least one Critical or High event in the window. Content and web events have no severity, so this is driven by file events only.
Off-Hour Activity n (p%) File + content events outside the tenant's business hours, in local time. The percentage denominator excludes web requests — it is a share of file+content, not of everything. The tile's own caption names the hours and zone used.
Policy Compliance Allowed ÷ all events, including web. Must equal the Security Score card's Compliance row exactly — they were two different numbers until D2 was fixed in this build.
File / Content / Web area cards All events in that area, split by channel (or by outcome, for web). The channel rows must sum exactly to the card's event count.
Risk Score Breakdown bars The snapshot's component percentages, averaged. They are shares of the risk model, not percentages of events, and they are not required to total 100.
Incidents by Area time-series with splitBy:"area" — one point per day per area. Quiet days are seeded as 0 rather than omitted, so the line is continuous.
High Risk Users list Top 6 users by Critical + High count, among users who have at least one. The headline tile counts all such users; the list shows 6. 10 vs 6 names is correct.
Endpoint Coverage Active endpoints by their latest daily status. Four buckets: Healthy, Offline, Service not running, Not reporting. "Not reporting" = registered but never heard from. The four must sum exactly to Total Endpoints — that is the strongest check on this card.
Security Score Score = compliance %, over the same population as the headline tile — file, content and web. Active/Total Policies counted from the policy tables, not from policy names in logs. "Needs review" = active policies with more than 10 non-Allowed events in the window, counted across the activity log and the web log together. Compliance here must equal the headline Policy Compliance tile (I18), and "x of y need review" must have x ≤ y.
Top Incidents by Apps Non-Allowed events grouped by application, device traffic excluded. Aggregate rows — they open the drill-down panel, never a single event.
Activity Heatmap File + content events by weekday and hour, tenant local time. Honours the header's Filter controls — if you filter to one user the grid must thin out.
Data Classification Scanned vs violated volume by detected category. A file carrying PII and PCI counts under both. The rows are "how much of this type did we see", not a partition, so they will not sum to the scanned total.
Insider Risk Signals Three computed rules: High-Risk User, After-Hours Transfer, Mass Data Exfiltration (>500 MB in 30 min, or >100 files in 15 min). Computed live from events, not stored flags. There is no filter that reproduces one exactly, so the panel a card opens is an approximation by design.

The drill-down panel — how it is supposed to behave

One endpoint serves every click on the dashboard. The request body is the question; the panel is the answer.

In the panelMust be
EventsThe same number as the thing that was clicked.
Blocked≤ Events, with the percentage of Events in brackets.
UsersDistinct users across the matched events — never the sum of per-source counts.
Top users chipsTop 4 by event count. Clicking one re-opens the panel as the same filter AND that user, with a back arrow.
"LATEST 60 OF n"n = total matches; the list holds min(60, n) rows, newest first. The caption appears only when n > 60.
Every listed eventMust satisfy every filter that was sent. Fields are AND'ed; values inside one field are OR'ed.
The headingSet by the UI from the tile that was clicked — the API deliberately returns no title, because one query serves many labels.
BackThe UI's own filter stack. The API returns no back pointer.
The triage rule for this panel. When the panel looks wrong, read the request body first.
  • Panel shows more than the widget → the UI sent too few filters (usually a missing areas — defect D1).
  • Panel is empty → either a filter that cannot match the population (channel/severity/ dataType against web), or a department that matches nobody.
  • Panel shows the right count but the wrong rows → a genuine API defect. Raise it with the body.

Numbers that must agree — the checks worth automating

Each of these should hold for any window, any filter. A break is a real defect.

#Check
I1Overview File/Content/Web card events = sum of that card's channel (or outcome) rows.
I2File Sharing tab Total File Events = the Overview File Sharing card, same window, same moment.
I3File Sharing: Upload + Download + Device Write + Device Read = Total File Events.
I4File Activity Split donut = the four KPI tiles, number for number.
I5Risk by Channel: a channel's Critical+High+Medium+Low+Not-assessed = that channel's Events.
I6Risk by Channel: a channel's Events = that channel's KPI tile.
I7Content: Blocked + Warned + Override + Allowed = Total Content Events.
I8Web: Blocked + Warned + Allowed = Policy-Matched Requests.

I11Drill-down Events = the widget that was clicked (once the UI sends areas).

I21A Top AI Tools row opens a panel whose Events equals the row. new — D5
I22The Off-Hour Activity tile opens a panel whose Events equals the tile, and that panel is smaller than the same window unfiltered. new — D7

I24A data-type panel is never larger than the card row that opened it. new — D8
I25A High-Risk Users row's violations equals {"areas":["file","content"],"userIds":[n],"actions":["Blocked","Warned","Override"]}, and the Total Violations box equals the same call with all six ids. new — D9
I20's "allowance" is real and is not a bug. Sensitive Data Detected counts identifier mentions, while the panel counts events. One prompt whose content carries two identifiers that both resolve to PII — say an email address and an Aadhaar number — adds 2 to the card's PII row and 1 to the panel. So the card can legitimately read higher. What it must never do is read higher because the filter found nothing: a 0, or a number that is a small fraction of the tile, is the D4 symptom returning.
I17 is the sharpest test you have, because it makes a headline tile and the drill-down behind it prove each other. If they ever differ, one of the two has changed its definition of "incident".

Looks wrong, is correct — please do not raise these

  1. Tab totals drift while you test. The data is live. Compare responses captured in the same minute.
  2. The three area cards do not sum to Total Incidents. Incidents counts Blocked + Warned + Override only; the cards show every event.
  3. There is a fifth severity, "None" / "Not assessed". The scanner emits it when it could not assess a file, and it is usually the largest bucket. The four coloured severities are not expected to sum to the total.
  4. Content and web events have no severity. Grey bars and zero severity columns on those tabs are correct.
  5. Copy / Paste and Typed Content are Content Sharing, not File Sharing. They used to land on the File tab; that was the bug and it is fixed. If you are comparing against an older build, the numbers have moved and the new ones are right.
  6. Device Write / Device Read carry events that used to be counted as Upload / Download. Expect Upload to be lower than in an old build and the two device channels to be higher by the same amount.
  7. Data Classification rows do not sum to the scanned total. A file with PII and PCI counts under both categories.
  8. Sensitive Data Detected percentages do not sum to 100. Same reason, over type-mentions.
  9. Top Destinations does not sum to Total File Events. Device traffic is excluded; it has its own card.
  10. Top AI Tools does not sum to the prompt total. Applications that are not GenAI tools are excluded by catalogue.
  11. Uncategorised is the biggest web category and still sorts last. Deliberate.
  12. Only Largest Transfers rows open a single event. Every other ranked list is an aggregate, so it has no event id — by design.
  13. A change badge is missing. null means "do not render" — the previous window had nothing, or no dates were sent.
  14. Endpoint Coverage has no "Warning" slice. "Service not running" is the derived equivalent: online, but DLP is not running. There is no stored Warning status.
  15. This tab's web numbers differ from the Logs screen's Web Filtering group. Different populations — see The three populations.
  16. Risk by Channel lists channels with 0 events. Keeps the table's shape, so 0 reads as "nothing happened" rather than "not measured".
  17. An Insider Risk Signal card opens a panel that does not match its number exactly. The signals are computed rules; no single filter reproduces one. Documented approximation.

Defects found in this review

Three were found. Two were on our side and are fixed in this build — they need a retest, and D2 deliberately moves a number, so read its side effect before raising anything. D1 is in the UI and is still open.

BLOCKER   D1 — the drill-down panel is not scoped to the tab it was opened from
Owner: UI. The API is behaving correctly; the request being sent is wrong.
StepsDashboard → File Sharing tab → Data Classification card → click PII.
Sent{"fromDate":"…","toDate":"…","dataTypes":["PII"]}
ExpectedOnly file events (Upload / Download / Device Write / Device Read) carrying PII. The panel's Events should equal the PII row on the card that was clicked.
ActualEvents is larger than the card, and the list contains rows like Selva S · Prompt · www.google.com. Prompts are Content Sharing events, so the panel is showing file and content merged.
Whydrill-down is one endpoint over all three populations and the request body is the only thing that names one. With no areas in the body it answers "file and content", which is exactly what it was asked. There is no tab in the URL and no session state for the server to infer from.
FixEvery click that originates on a tab must send that tab's area — "areas":["file"], ["content"] or ["web"] — in addition to whatever the widget contributes. So the case above becomes {"areas":["file"],"dataTypes":["PII"]}. The per-tab click→filter table in Dashboard-V2-API-Documentation.html → Click → filter map has been rewritten to spell out the exact body for every widget on all four tabs.
RetestFor each of the four tabs, click every clickable widget and confirm (a) the request body carries the tab's areas, and (b) I11 holds — the panel's Events equals the widget's own number. On File Sharing, no listed row may have a Prompt, Copy / Paste or Typed Content channel; on Content Sharing, none may be an Upload or Download.
FIXED IN THIS BUILD   D2 — two different "Compliance" numbers on the Overview
Owner: API. Fixed — retest required.
WasThe headline Policy Compliance tile and the Security Score card's Compliance row showed different percentages on the same screen for the same window — observed 11% and 15%.
CauseDifferent populations. The headline divided by all events including web requests; the Security Score card divided by file + content only. Web requests are almost entirely blocked, so including them pulls the figure down. Neither number was wrong on its own; having both under one word was.
NowBoth count all three areas. They must agree exactly — that is invariant I18.
Side effect to expect"N policies need review" will go up on any tenant with active web policies. It too now counts a policy's noise across the activity log and the web log together, so a web policy that blocked several hundred requests is finally named by the card that scores it. A rise here is the fix working, not a regression.

FIXED IN THIS BUILD   D3 — the same domain appeared twice in Top Blocked Domains
Owner: API. Fixed — retest required.
Waschatgpt.com listed twice — 146 blocks as Uncategorised and 40 as Computers And Technology — and likewise claude.ai at 56 and 19. One domain's block count was split across two ranks, so neither row said how often that domain was really blocked, and a domain with an even split could be pushed off the six-row card by one it actually outranks.

FIXED IN THIS BUILD   D4 — a data-type click opened an empty or short panel
Owner: API. Fixed — retest required. Raised by the API team against 11–17 Nov.
Was{"areas":["content"],"dataTypes":["POLICY"]} returned totalCount 0 while Sensitive Data Detected read 615 for POLICY, so the panel opened empty. PII read 285 on the tile against 201 in the panel; PCI 84 against 67.
CauseThe card and the filter spoke different vocabularies. The card resolves every stored identifier through the sensitive-category catalogue and reports the category — so "EMAIL ADDRESS" counts under PII — while the filter compared the requested string against the stored one directly. FIXED IN THIS BUILD   D5 — an AI-tool click returned a fraction of the row
Owner: API. Fixed — retest required.

CauseThe same shape as D4. Top AI Tools groups prompts by the catalogue's display name, so Claude, claude.ai, Claude.exe and a browser-extension id are one row — while the filter matched the stored application name exactly, finding only the rows literally recorded as "Claude".

Round-one test checklist

  1. Baseline. Pick one window (e.g. last 7 days) and capture all four tabs' API responses within the same minute. Every later comparison uses these, not screenshots.
  2. Invariants. Run I1–I10, plus I18 and I19, against the captured responses. These need no clicking.
  3. Tab scoping (D1). On each tab, click every clickable widget. For each: capture the request body, confirm it carries the tab's areas, and confirm I11.
  4. Population leakage. In every File Sharing panel, confirm no row has a Prompt / Copy / Paste / Typed Content channel. In every Content Sharing panel, confirm no Upload / Download / Device row. In every Web Filtering panel, confirm every row is a domain.
  5. Composition. Open any panel, click a user chip, confirm the count narrows (I14) and the back arrow restores the previous filter and count exactly.
  6. Event detail. Expand a panel row; confirm it opens the right event. Then confirm that the same id under the wrong area returns 404 rather than someone else's event — the three populations have overlapping id sequences.
  7. Header filters. Apply Severity / Action / Department from the header and confirm every card on the page moves, including the Activity Heatmap. A card that does not move is not reading the filter.
  8. Department. Filter to a department with no users and confirm the page reads zero everywhere rather than showing everybody.
  9. Date edges. Single day; a day with no events; a window ending today; no window at all (all badges must disappear). Confirm I15 across a widening range.
  10. Time zone. Confirm the Off-Hour tile and the heat map both name Asia/Kolkata and the tenant's business hours, and that an event just outside those hours is counted as off-hours.
  11. Degraded paths. A window with no risk snapshots → "Unknown", not a score of 0. A tenant with no endpoints → Endpoint Coverage reads 0 of 0, not an error.
  12. Performance. Overview should be 6 calls, each a few hundred ms. A tab that fires more than its documented calls, or one call per card, is a regression.
