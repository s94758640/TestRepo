The override flow

A policy blocks a transfer. The employee can ask for that block to be lifted, by one of two routes the policy decides per severity:

RouteWhat happens
SelfOverride stored as 1Auto-approved at submit. The request row is written already APPROVED, with ValidFrom/ValidUntil set, and the activity is flagged IsOverrideApplied. It spends one of the user's allowance for the reset period. An admin can close the window early with RevokeSelfOverride.
AdminApproval stored as 2Written PENDING; the activity is flagged IsPendingApproval and the DLP admins get a Recent Alerts notification. Nothing unlocks until someone calls ReviewOverrideRequest. The approver roles allowed to decide it are frozen onto the row at submit.

Both routes write one row of dlp."OverrideRequest". The same table backs file overrides (ActivityId = the activity's EnrichedId) and AI prompt overrides (ActivityId = 0, AiPromptBlockLogId set).

Which rules apply — since 23 Oct 2026 every override endpoint resolves its rules from the published PolicyV2 Response options (the override matrix: severities → route → unlock duration → approver roles), falling back to TrayAppSettings in appsettings when the tenant has no published V2 policy. The legacy dlp."PolicyActionSettings" booleans are deliberately not read.

Route aliases. SubmitPolicyOverrideRequest and GetUserPolicyOverrideSettings were added while the tray team was moving to the new policy. Both now behave identically to the original routes — same contract, same rules. New callers should use SubmitOverrideRequest and GetUserOverrideSettings.

Conventions & headers

HeaderRequiredNotes
ClientGUIDrequiredTenant identifier — selects the tenant's DLP database. Without it the request falls back to DefaultConnection and reads the wrong tenant.
Content-Typerequiredapplication/json on every POST.
Authorizationsee belowTray and agent endpoints are [AllowAnonymous] and identify the user by userId in the body or query. Portal endpoints need a Bearer JWT. On the approval grid a JWT with a UserId claim removes the need for ?userId=.
Routes have no controller prefix. Every endpoint below sits at the host root — POST https://{dlp-api-host}/SubmitOverrideRequest, not /api/TrayApp/....
Dates are ISO-8601 UTC; the server clock decides every window, so never compute an expiry from the endpoint's own clock. JSON is camelCase. Every response uses the envelope { success, message, data, errors } — the samples below show the data shape only.
Who is marked ANON / JWT

ANON — [AllowAnonymous]: reachable by the tray app and the agent with no token. JWT — requires a Bearer token. Note that the approvals endpoints are anonymous too: canApprove is a display flag, and server-side enforcement of who may decide is not wired yet (see known gaps).

Error codes TrayAppErrorCodes — stable, safe to switch on
CodeHTTPMeans
NOT_ALLOWED400The policy does not permit this route, or not for this severity. Don't retry; offer the other route if the policy allows it.
LIMIT_EXCEEDED409The self-override allowance for the period is spent, or the requested duration is over the ceiling. On a review, the approver asked for more time than the policy allows (400).
DUPLICATE_REQUEST409A request for this activity is already pending — usually a double click. Refresh, don't resubmit.
ALREADY_DECIDED409 / 400Someone already approved or rejected it. The first decision stands; refresh the row.
FORBIDDEN400The caller is not the requester (cancel), or may not see/decide approvals.
On a refusal both levels say failure: the envelope's success is false and data.success is false with data.errorCode set. Read errorCode, never the message text — the wording changes.

Channels NEW

An override now records where it applies, as a pair: channelType — "App" or "Site" — and channelName, the channel itself.

App

The application the user was working in: TeamsOutlookSlackOneDriveFile Explorer and anything else the log names.

Site

The web destination the file was going to: OneDriveSharePointGoogle DriveDropboxChatGPT, or the host itself for anything unrecognised (vendor-portal.com).

How the pair is filled
What the caller sendsWhat is stored
Both fieldsExactly that — the caller knows things the log does not.
channelName onlyThe name as sent, plus the derived type when the two agree on the channel, "App" otherwise. A named channel is never left untyped.
NeitherDerived from the activity's own application and URL, so a client that never heard of the field still stores a channel.
A browser is never the channel. Chrome uploading to OneDrive is a OneDrive transfer. So a known non-browser application wins first, then the site, then whatever application was left. chrome.exe + onedrive.live.com → Site / OneDrive; teams.exe with no URL → App / Teams.
Null and empty are valid. Both fields null means the override covers every channel — which is how every override behaved before the column existed, so rows written before this change, and any activity naming neither an application nor a URL, keep working untouched. Treat null as "no channel restriction", never as a miss.

Stored as dlp."OverrideRequest"."ChannelType" varchar(20) and "ChannelName" varchar(100); a longer value is cut, not rejected. Returned by CheckOverrideStatus. Prompt overrides do not set a channel.

Durations & limits

A request may say how long access is wanted: requestedDuration (a number) plus durationUnit ("Hours" or "Days", defaulting to Hours). Both are optional — omitting them keeps the pre-existing behaviour (the configured default window).

RuleEffect
A policy matrix rule covers the activity's severityThe rule's unlock duration wins over whatever the employee asked for, and the ceiling check is skipped.
Rule preset is OneUploadThe row stores durationUnit: "OneUpload" so the agent can enforce single use; validUntil is a 60-minute grace window.
No matrix rule, self overrideCapped at maxSelfOverrideHours (from GetUserOverrideSettings); over it → 409 LIMIT_EXCEEDED.
No matrix rule, admin approvalCapped at maxAdminApprovalDays; over it → 409 LIMIT_EXCEEDED.
AllowanceselfOverridesRemaining <= 0 → 409 LIMIT_EXCEEDED. 0 means zero, not unlimited; unlimited is signalled by isUnlimitedSelfOverrides: true (totals then carry int.MaxValue — render "Unlimited", not the number).
What the approver may grant

On approve, the Access Time dialog sends grantedDuration + grantedDurationUnit. The window is resolved in this order: 1. what the approver chose · 2. what the employee asked for · 3. the configured default (AdminApprovalValidityDays). An approver may shorten a window, never extend it past policyTimeLimitMinutes on the row — the dialog should cap at that value ("Up to 3 Days", policyTimeLimitSetBy names the policy).

The new fields
FieldMeans
isExpiredtrue once validUntil has passed, on the minute. false when the window is still open and when there is no window at all — a pending, rejected or cancelled request was never open, so it is not expired.
validUntilWhen the granted window closes, server clock. null while pending, on a rejected or cancelled request, and on an approval given no end.
channelType / channelNameWhere the override applies — see channels. Both null means every channel, which is what every override before this change meant. Do not treat null as a non-match.
isOverrideApproved is unchanged: it still reports the stored decision alone, so an approved-but-expired request still reads true there. That is deliberate — agents read it today, and flipping it would silently change what they release. Check isExpired as well before releasing a held transfer. The message now says "approved but expired at …" in that case.
The same four fields are on GET /CheckMetaStatus (override status plus the MetaId's rename history) and on the ExeApi twins V1/CheckOverrideStatus and V1/CheckMetaStatus — one shared mapper, so the hosts cannot disagree. CheckOverrideStatus is marked TEMPORARY in the code: anonymous until the agent credential scheme lands.

AI prompt overrides

Blocked AI prompts use the same OverrideRequest table, the same approval queue and the same monthly allowance pool, anchored on AiPromptBlockLogId instead of an activity. These three routes mirror ExeApi's V1/… versions and exist here because the EXE agent still points at this API. Approving or rejecting one goes through the ordinary ReviewOverrideRequest.

Deployment note (SQL)

The channel pair is two new columns on dlp."OverrideRequest":

SFM.DLP.Infrastructure/Data/Migrations/AddChannelToOverrideRequest.sql

ALTER TABLE dlp."OverrideRequest" ADD COLUMN IF NOT EXISTS "ChannelType" varchar(20)  NULL;
ALTER TABLE dlp."OverrideRequest" ADD COLUMN IF NOT EXISTS "ChannelName" varchar(100) NULL;
-- plus a narrow backfill from the row's existing Destination / Application
Run it before deploying the API, against every client database. EF selects both columns on every OverrideRequest query, so a database without them fails the approvals screens, the tray dialogs and the agent's status checks — not just the new fields. The script is guarded and safe to re-run.

The backfill is deliberately narrow: only the handful of hosts and applications the resolver names the same way, so backfilled rows and new rows agree. Everything else stays null, which already means "every channel". isExpired and validUntil need no migration — they are computed from the column that was always there.
