Agent Override API Update

For the EXE / agent team · 28 Oct 2026 · two additive changes to the override endpoints

What changed

ChangeWhereAgent impact
Expiry is now reported — isExpired and validUntil CheckOverrideStatus, CheckMetaStatus The agent can tell a live grant from a lapsed one without doing its own clock arithmetic.
Channel is now recorded — channelType + channelName SubmitOverrideRequest (in), status endpoints (out) An override says where it applies: App/Teams, Site/OneDrive. Optional to send; always returned.
Both are additive. No request field became required, no existing field changed meaning, and no status code moved. An agent build that ignores all of this keeps working exactly as it does today.

The one behaviour to adopt

isOverrideApproved has not changed: it still reports the stored decision alone, so an approved override whose window closed three days ago still comes back true. That was left alone on purpose, because agents read that flag today and flipping it would have silently changed what gets released.

So the release check gains one condition:

// before
if (status.IsOverrideApproved) Release();

// now
if (status.IsOverrideApproved && !status.IsExpired) Release();
Do not add a channel condition unless you need one. channelType / channelName are informational for the agent — they describe the transfer the override was raised on. A null pair means "every channel", so treating null as a mismatch would hold transfers that should go through.

The new fields

FieldTypeMeaning
isExpired NEW bool true once validUntil has passed, to the minute. false while the window is open and when there is no window at all — a pending, rejected or cancelled request was never open, so it is not expired.
validUntil NEW DateTime? When the granted window closes, UTC, server clock. Null while pending, on a rejected or cancelled request, and on an approval that was given no end. Never compute expiry from the endpoint's own clock — it can be wrong or deliberately set.
channelType NEW string? "App" or "Site". Null = every channel.
channelName NEW string? "Teams", "OneDrive", or a bare host. Null = every channel.

Message text

When a grant has lapsed, message now reads "Override request is approved but expired at 2026-10-27 18:30:00Z" instead of "Override request is approved". Branch on isExpired, not on the sentence.

If you send nothing

The server derives the pair from the activity's own application and URL, so an agent build that never heard of these fields still produces a usable channel. Sending them is worth it only when the agent knows something the log does not.

What you sendWhat is stored
Both fieldsExactly that.
channelName onlyYour name, plus the derived type when both describe the same channel, "App" otherwise. A named channel is never left untyped.
NeitherBoth derived from the activity.

Response shape is unchanged: { success, message, errorCode, overridesRemaining, accessExpiresAt }. The refusal codes (NOT_ALLOWED, LIMIT_EXCEEDED, DUPLICATE_REQUEST) are unchanged, and no new one was added for channels — a channel never causes a refusal.

An unrecognised application keeps its own name, minus the .exe: acmesync.exe → Acmesync.

Site

The web destination the file was going to.

OneDriveSharePointGoogle DriveGmailOutlook WebTeamsSlackDropboxBoxWeTransferGitHubGitLabChatGPTClaudeGeminiLinkedInFacebook

An unrecognised host is used as-is, without www.: vendor-portal.com.

A browser is never the channel. Chrome uploading to OneDrive is a OneDrive transfer, so the rule is: a known non-browser application wins first, then the site, then whatever application was left.
chrome.exe + onedrive.live.com → Site / OneDrive
teams.exe, no URL → App / Teams
Null and empty are valid and mean "every channel" — which is how every override behaved before this existed. Rows written before the change, and any activity naming neither an application nor a URL, stay null. Treat null as "no channel restriction", never as a miss. Values are cut at 20 characters (type) and 100 (name) rather than rejected.

Not changed

  • V1/SubmitPromptOverrideRequest, V1/CheckPromptOverrideStatus, V1/CancelPromptOverrideRequest — prompt overrides store no channel (null = every channel), and CheckPromptOverrideStatus already took the window into account when answering isOverrideApproved.
  • V1/CancelOverrideRequest — same body, same rules.
  • Allowances, duration ceilings, the policy override matrix, approver roles and every refusal code.
  • Auth: these routes stay anonymous until the agent credential scheme lands. ClientGUID is still required on every call.

Rollout order

  1. Database first. AddChannelToOverrideRequest.sql adds two nullable columns to dlp."OverrideRequest" and backfills a narrow set from the data already on each row. It runs per client database and is safe to re-run.
  2. Then the API — both hosts, together: the container API and ExeApi read and write the same table.
  3. Agent whenever. Nothing in the agent has to ship with it. Pick up isExpired when convenient; send the channel fields only if you want to override the server's derivation.
Until the API deploys, the four new fields are simply absent from the response — deserialise them as optional. Until the SQL runs, the API must not be deployed at all: every OverrideRequest query selects the two new columns.
