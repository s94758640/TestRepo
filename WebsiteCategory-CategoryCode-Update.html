2. The AI service behind it (backend reference)

Callers never talk to this directly — WebsiteCategoryService does — but this is the new contract:


# 1. Login (token cached in-process, refreshed 300 s before expiry, one retry on 401)
POST https://qa-agent-chatbot.whitegrass-abb3b3ae.eastus2.azurecontainerapps.io/login
Body: { "username": "…", "password": "…", "name": "…" }
→ bearer token (token.access | access_token | token accepted)

# 2. Categorise
POST https://qa-agent-chatbot.whitegrass-abb3b3ae.eastus2.azurecontainerapps.io/categorize-website
Header: Authorization: Bearer <token>
Body:   form-encoded   url=https://www.wikipedia.org

Response:
{
  "url": "https://www.wikipedia.org",
  "domain": "www.wikipedia.org",
  "category": "Reference",
  "subcategory": "Encyclopedias",
  "category_percentage": 100.0,
  "subcategory_percentage": 100.0,
  "vulnerability": "Safe"
}

category/subcategory map to topCategory/topSubCategory and are stored verbatim, exactly as the old field names were. vulnerability is parsed but not stored or returned yet. If a deployment still sends the old top_category/top_subcategory names, they are accepted as fallbacks.

3. CheckWebSiteCategory — the two new fields

Both routes (POST /CheckWebSiteCategory on the DLP API, POST V1/CheckWebSiteCategory on the ExeApi) return the same response as before, with two additions:


{
  "success": true,
  "message": "Success",
  "data": {
    "url": "https://www.wikipedia.org/",
    "domain": "www.wikipedia.org",
    "topCategory": "Reference",
    "categoryPercentage": 100.0,
    "topSubCategory": "Encyclopedias",
    "subCategoryPercentage": 100.0,
    "topCategoryCode": "REFERENCE",        ← NEW
    "topSubCategoryCode": "ENCYCLOPEDIAS", ← NEW
    "fromCache": false,
    "categorizedAt": "2026-10-12T09:14:02Z"
  },
  "errors": null
}

The codes are a stable, deterministic form of the AI's labels: uppercase, every run of non-alphanumeric characters becomes one underscore, no leading/trailing underscore. They exist so the exe compares codes, never display names:

LabelCode
ReferenceREFERENCE
Social MediaSOCIAL_MEDIA
Malware & PhishingMALWARE_PHISHING
Photo and Video SharingPHOTO_AND_VIDEO_SHARING
E-commerceE_COMMERCE

Null label → null code. Cached rows categorised before this change return codes too — the derivation runs at read time, not at store time.

4. PolicySnapshot — what the exe matches against

Each web category the policy references now appears in catalogRefs.webCategories with three fields:


"catalogRefs": {
  "webCategories": [
    { "code": "ADULT",    "name": "Adult Content", "categoryCode": "ADULT_CONTENT" },
    { "code": "GAMBLING", "name": "Gambling",      "categoryCode": "GAMBLING" }
  ]
}
FieldMeaning
codeThe hand-written catalog code. This is the key used inside the policy document — modules.webFiltering.customRules.restrictedCategories and siteOrCategory.value refer to it. Unchanged.
nameThe category's display name, for logs and debugging.
categoryCodeThe match key. Derived from name with the same rule as §3, so it is directly comparable with the verdict's topCategoryCode / topSubCategoryCode.
Why not match on code? Catalog codes are hand-written and don't always equal the derived form — "Adult Content" is ADULT in the catalog but derives to ADULT_CONTENT. categoryCode removes that drift: both sides of the comparison come from one shared derivation.

4.1 Exe matching recipe


verdict = CheckWebSiteCategory(url)        // topCategoryCode, topSubCategoryCode

for ref in snapshot.catalogRefs.webCategories:
    if ref.categoryCode == verdict.topCategoryCode
    or ref.categoryCode == verdict.topSubCategoryCode:
        matchedCatalogCode = ref.code      // e.g. "ADULT"
        break

// Then apply the policy using matchedCatalogCode against
// modules.webFiltering (restrictedCategories / siteOrCategory.value).

Compare against both verdict codes: a catalog entry like "Social Media" may arrive from the AI as the top category of one site and the subcategory of another. Case-sensitive compare is fine — both sides are already uppercase.

5. Behaviour that did not change

  • Request shape, URL normalisation, per-domain tenant cache, fromCache, error statuses (400 / 502 / 500) — all exactly as in the original guide.
  • master."WebsiteCategory" — no new columns, no migration, no backfill.
  • The policy document itself (modules.webFiltering) — still keyed by catalog code.
  • Snapshot hash semantics — the hash still covers the compiled payload; it simply changes on the next publish because the payload gained fields.

  2. Deploy SFM.DLP.API and SFM.DLP.ExeApi. No SQL to run.
  3. Republish policies that use web filtering. categoryCode/name are added when a snapshot is compiled, so an already-published snapshot doesn't have them until its policy is republished (agents then pick up the new snapshot on their next PolicyCheck — the hash changes).
  4. Verify: POST a URL to CheckWebSiteCategory and see the two code fields; fetch V2/PolicySnapshot for a republished policy and see categoryCode under catalogRefs.webCategories.
One rule to protect: the code derivation is shared by both APIs (WebsiteCategoryCodes.ToCode, locked by unit tests). Changing it — or renaming a WebCategory display name — breaks matching until every affected policy is republished.
