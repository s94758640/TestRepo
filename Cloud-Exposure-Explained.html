What Blast Radius is counting

Every sensitive file we find in a connected cloud gets one word describing how far it reaches. Four words, and a file always gets the widest one that is true of it. This page says what each means, and explains the three numbers above the grid.

The four levels

  1. Restricted Named people only

    Only the people it was explicitly given to can open it.

    This is also what "not shared at all" looks like. A file nobody has shared is Restricted — the level means nothing reaches past the named people, not that somebody chose a restriction.

  2. OrgWide Anyone signed in

    Anyone inside the company who is signed in can open it.

    A link of the "people in your organisation" kind. No outsider can use it — they would have to sign in, and they cannot — but it is no longer limited to the people who were given it. Every employee can reach it.

  3. External Someone outside the company

    At least one named person on it does not belong to the company.

    Decided by the email domain of each person the file is shared with, checked against the tenant's own verified domains as the provider reports them — not guessed from the file owner's address. Most tenants have more than one domain, and guessing would turn colleagues into outsiders.

  4. PublicLink No sign-in needed

    Anyone holding the link can open it, signed in or not.

    The widest answer there is. Nothing outranks it, so the moment one anonymous link is found the file is Public and the other permissions stop mattering.

One file, one level — the widest that is true

A file can be shared several ways at once. The level is not a list; it is the single worst case. Take a budget spreadsheet with three permissions on it:

  1. The finance team, by name — on its own, Restricted
  2. An "anyone in the organisation" link — on its own, OrgWide
  3. One "anyone with the link" link — on its own, PublicLink
This file counts once, as PublicLink

If it were counted at its narrowest, a single tight permission would hide a public link behind it. That is the one mistake this grid exists to prevent, so the rule is worst-wins and it is never averaged.

Before you raise it as a bug

"Sensitive" here will not match the Sensitive tile at the top of the page.

The grid has one row per classification, and a file carrying two classifications is counted under both. A spreadsheet holding PII and PFI appears on the PII row and on the PFI row, so the grid's total runs ahead of the number of files.

The tile counts files. The grid counts classified objects. Both are right; they answer different questions. Expect the grid's total to be the larger of the two.

External is only known for files the provider already told us were shared.

Working out who a file reaches needs a separate permissions request per file. Asking that for every file in a tenant is the difference between a scan and getting throttled, so we ask only about files the provider has flagged as shared.

A file nobody shared has nothing to say, so nothing is lost — but read the figure as external among shared files, not a sweep of everything.

The other screen — Public Links in Circulation

Same data, one level down. Exposure is the verdict on a whole file after looking at every permission on it. A link is one of those permissions. This screen lists the links themselves — so one file can appear more than once, with a different row for each way it is shared.

"In circulation" means someone could open it today.

The list only carries links that still work. A link that has been revoked, or one on a file that has since been deleted, never appears here.

Revoked links are not thrown away — "this was public for six weeks and is not any more" is exactly what an investigation needs — but a list headed in circulation must not carry them. So the count answers "what could be opened right now", not "what has ever been shared".

Two things to know before raising a bug

The heading says "Public Links" on every tab — but only the first tab is public.

On Every link the figure counts links of all three kinds, so a number far larger than the public one is correct, not a defect. A tenant with 144,504 under that heading does not have 144,504 public links.

What is worth reporting is the heading: it should follow the tab, or say something neutral like "Sharing links in circulation" with the public figure shown on its own.

Leaving the filter out is not the same as clearing it.

If you are testing the API directly rather than clicking the tabs, these two requests give different answers:

{"page":1,"pageSize":100} → public links only, because leaving the field out keeps the screen's own default.

{"scope":null,"page":1,"pageSize":100} → every link, because sending it empty clears the filter.

The tabs send the second form, so the screen is right. It is only hand-written requests that can trip on this — and "no filter gave me fewer rows" reads exactly like a bug when it is not.

Where this comes from: CloudExposurePolicy.Derive decides a file's level, POST /cloud/overview returns the Blast Radius grid, and POST /cloud/links returns the links list. The level is stored per file on discovery."CloudFile"."ExposureLevel" and recalculated from the live permission rows on every crawl.
