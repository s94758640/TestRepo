What changed

29 Oct 2026 · answering the review of this API, then the QA findings · branch feature/feedback

  • Linked log file name is the file name again. linkedLog.fileName and the grid's linkedLogFileName were returning the agent's whole path (C:\Users\…\PHI.pdf). The API runs on Linux, where a backslash is an ordinary filename character, so the Windows path was never split. Both now take the last segment on either separator. Rows already stored keep the full path — the value is a snapshot taken at submit time, so only feedback raised after this deploys is corrected.
  • Description is now optional for FalsePositive and FalseNegative, as the design has it. Still required for every other type. A multipart submit was being refused by model binding before that rule could run — 400 "Description: The Description field is required." — because the field was declared non-nullable and MVC treats that as implicitly required. The field is nullable now, so the only thing deciding this is the rule above.
  • The grid row carries the Linked Log, so no detail call per line. linkedAiPromptBlockLogId, linkedLogActivity and linkedLogApplication are on every feedback/list row now. A prompt has no file name, so those rows previously showed "--" and were indistinguishable from feedback linked to nothing; render them as activity · application ("Prompt · desktop"). The CSV export composes the same cell, falling back to PROMPT-4768. LinkedLogActivity and LinkedLogApplication also work as likeFilters keys — they always did; the key list on this page was incomplete.
  • A feedback linked to a blocked AI prompt now gets a Linked Log card. Sending LinkedAiPromptBlockLogId stored only the id and the category, so the card rendered as dashes. The snapshot is now taken from the prompt-block log at submit time, the same as a transfer: displayId (PROMPT-4768), status, activity, application, destination, policyName, userName and receivedTime. fileName stays null — a prompt has no file. Existing rows keep their empty copy; re-test with a new submission.
  • Attachments download under their own name. The link now carries a signed Content-Disposition, so a file saves as Screenshot - DLP > Logs.png instead of the storage guid.
  • Casing: nothing to change, and the examples on this page were wrong. Every endpoint returns camelCase — success, message, data, totalCount, feedbackId — and always has; all three hosts register MVC with AddNewtonsoftJson, which camel-cases property names. This page showed PascalCase throughout, which is the likeliest source of the report. Every example is now what the wire actually carries. data.message on a 400 works today. See Casing for the two things that are not camel-cased.
  • Your feedback is scoped by the token. feedback/list no longer returns everyone's rows to everyone: an admin reads the tenant's, everyone else reads their own. The scope is applied under the request, so raisedByUserId in the body can narrow your own rows but never widen them. It covers the detail, attachment URLs, comments and triage too — the attachment route in particular used to mint a working link for anyone holding an id. NEW GET / POST feedback/mine for the "My feedback" tab — no user id to send.
  • No route returns 403. Access is scope, not refusal: feedback you may not touch is a 404, on triage as well as read. There is no forbidden state to design for — if a row came back from the grid, every action on it will work.
  • The ID column filters now. DisplayId is not a stored column, so it was being dropped silently and the column filtered on nothing. Both displayId and feedbackNumber now read the digits out of FB-2052, fb2052 or 2052, exact or partial. subject, linkedLogFileName and raisedByName already worked as likeFilters — the key list on this page was just incomplete. raisedByUserId is confirmed exact-match only.
  • A FEEDBACK permission module with VIEW and EDIT is added to the role catalog by migration V0002__feedback_permission_module.sql, so the admin grid can be permission-gated. It appears in GetModulesWithPermissions/1 once the environment is migrated — see Deployment note.
  • "View in Logs" already has a target — GET GetTransferLogDetails/{enrichedId} returns the same row shape as GetTransferLogs. No new route was needed; it is documented on the detail panel.
Not yet verified against a database. The above builds and the generated SQL was checked, but no request has gone through the stack yet. Treat the contract as firm and the behaviour as needing a QA pass.

What this is

Employees raise feedback from the tray app — a false positive, a bug, an idea. Admins read and triage it in the web portal, on the Feedback & Detection Reports screen. Feedback can optionally be attached to one DLP log, which the detail panel renders as the Linked Log card.

RouteWho calls itAuth
POST feedback/submittray app and portalnone required
GET feedback/lookupstray app and portalnone required
POST feedback/listportalBearer JWT — admin sees all, everyone else their own
GET feedback/mine · POST feedback/mineportalBearer JWT — always the caller's own
GET feedback/{feedbackId}portalBearer JWT — own feedback, or any if admin
GET feedback/attachment/{attachmentId}/urlportalBearer JWT — own feedback, or any if admin
PATCH feedback/{feedbackId}/statusportalBearer JWT — own feedback, or any if admin
POST feedback/{feedbackId}/assignportalBearer JWT — own feedback, or any if admin
POST feedback/{feedbackId}/commentportalBearer JWT — own feedback, or any if admin
POST feedback/exportportalBearer JWT — admin gets all, others get their own
Tray team: you only need the first two. Everything else is the admin screen.
Who sees what is decided by the token, not by the request body. A caller whose role name contains "Admin" reads the tenant's feedback; everyone else reads only what they raised, on every route — grid, counts, detail, attachment URLs, comments and triage alike. Sending someone else's RaisedByUserId in exactFilters narrows your own rows; it cannot widen them.
No route returns 403. Access is expressed as scope, not refusal: a feedback you may not touch is a 404, on read and on triage alike. So there is no "forbidden" state for the UI to render — if a row came back from the grid, every action on it will work.

The submit route also exists on the Functions host as POST V1/SubmitFeedback. Same service behind it, same request and response — see ExeApi V1 equivalents. Point at feedback/submit today; moving later is a URL change and nothing else.

Conventions & headers

HeaderRequiredNotes
ClientGUIDrequiredTenant identifier — routes to the correct tenant DLP database. Every call, including the anonymous ones.
Content-Typerequiredmultipart/form-data for a submit with attachments, application/json otherwise.
Authorizationsee table aboveBearer <jwt>. On feedback/submit it is optional: when present, the token's UserId claim wins over the UserId in the body.
Casing

Responses are camelCase — success, message, data, totalCount, feedbackId — the same as every other DLP, Identity and Nucleus endpoint. All three hosts register MVC with AddNewtonsoftJson, whose default naming strategy camel-cases property names. Read errors from data.message exactly as you do on the Logs screens.

Two things are NOT camel-cased, and both matter.
• Dictionary keys. Newtonsoft's camelCase strategy leaves them alone, so typeCounts and statusCounts come back keyed "FalsePositive", "InReview" — the stored values, which is what you filter by. The property is camelCase, the keys inside it are not.
• Filter keys you send. exactFilters / likeFilters are keyed by column name — "FeedbackType", "Subject". They are matched case-insensitively, so "feedbackType" also works, but the PascalCase spelling is the canonical one and is what this page uses.
Requests are case-insensitive. The body binder matches "pageSize" and "PageSize" alike, so an older client sending PascalCase keeps working. New code should send camelCase.
Envelope. Every JSON response is { "success", "message", "data", "errors" }. The samples below show the data contents only.
Dates. ISO-8601 UTC on the wire; the client localises.

Five things worth knowing about this response.
• totalCount is the count after filtering, before paging — use it for the pager.
• typeCounts and statusCounts are taken before the type and status filters narrow the set, so the dropdowns keep every option and show a count for each. Selecting "Bug" does not make every other option read zero.
• Their KEYS stay PascalCase — "FalsePositive", "InReview". Property names are camel-cased by the serializer; dictionary keys are not, and these keys are the stored values you filter by. Do not lower-case them before sending them back in exactFilters.
• raisedByInitials is computed server-side so the avatar chip matches everywhere.
• appliedSort.resolved is the sort actually used. If you send a key the server does not sort by, it falls back to RaisedOn and says so here rather than silently returning a different order.
A date with no time means the whole of that day. "toDate": "2026-10-26" includes everything raised on the 26th, not just 00:00.
2bGET/feedback/mine the "My feedback" tab

The panel's second tab — the signed-in user's own submissions ("My feedback 3"). The user comes from the token; there is no id to send and none to get wrong. Response is identical to feedback/list.

Example — the caller's own feedback, newest first
curl "{dlp-api}/feedback/mine?page=1&pageSize=25" \
     -H "ClientGUID: 11111111-2222-3333-4444-555555555555" \
     -H "Authorization: Bearer <jwt>"

Query parameters: page (default 1), pageSize (default 25, max 200), search, status. Sorting is RaisedOn descending.

Same thing with a full filter body

When the tab needs the grid's sorting or column filters, POST the same route with a feedback/list body. The scope still comes from the token.

curl -X POST "{dlp-api}/feedback/mine" \
     -H "ClientGUID: 11111111-2222-3333-4444-555555555555" \
     -H "Authorization: Bearer <jwt>" \
     -H "Content-Type: application/json" \
     -d '{
       "page": 1,
       "pageSize": 25,
       "sortBy": "RaisedOn",
       "sortDescending": true,
       "exactFilters": { "Status": ["New","InReview"] }
     }'

Render each card from the list item: DisplayId (FB-2038) · FeedbackType · PageModule on the first line, Subject as the title, RaisedOn below. TotalCount is the tab's badge number. Clicking a card opens the detail panel by FeedbackId.

Use this route rather than feedback/list with a RaisedByUserId filter. feedback/mine is scoped to the caller even when the caller is an admin, so an admin's "My feedback" tab shows their own submissions instead of the whole tenant's.

The Linked Log card is a snapshot, stored when the feedback was raised. It still reads correctly after the policy is renamed or the log is purged — which is the point.
Use IsResolvable to decide whether to show "View in Logs". When it is false the log row is gone and the link would lead nowhere; render the card without the link.

Attachment url expires after 15 minutes. Do not cache it or put it in a saved report. If a user leaves the panel open and the link stops working, re-fetch it:
GET /feedback/attachment/{attachmentId}/url → {"success":true,"data":"https://…"}
The link downloads under the original file name. Objects are stored under a guid, so the URL carries a signed Content-Disposition that saves the file as Screenshot - DLP > Logs.png rather than cdac2357-….png. It is signed into the URL, so editing the query string invalidates it. Azure and S3 only — the local FileSystem provider used in dev serves the stored name.
4PATCH/feedback/{feedbackId}/status

Move the item through New → InReview → Resolved or Closed. Two sibling routes sit beside it: POST .../assign and POST .../comment. All three return the updated detail object, so re-render the panel from the response instead of re-fetching.

Example — resolve it with a note
curl -X PATCH "{dlp-api}/feedback/8f0b1c2d-3e4f-5678-9abc-def012345678/status" \
     -H "ClientGUID: 11111111-2222-3333-4444-555555555555" \
     -H "Authorization: Bearer <jwt>" \
     -H "Content-Type: application/json" \
     -d '{ "status": "Resolved", "resolutionNotes": "Policy tuned to skip template files." }'
The other two
# assign — send "assignedToUserId": null to clear it
POST /feedback/{feedbackId}/assign    { "assignedToUserId": 907 }

# comment — IsInternal defaults to true
POST /feedback/{feedbackId}/comment   { "body": "Reproduced on build 1.01.011.", "isInternal": true }
Moving out of Resolved or Closed clears the resolution stamp — ResolvedByName and ResolvedAt go back to null, so a reopened item never claims it was closed by someone who has since been overruled.
Who did it is taken from the Bearer token. You do not need to send ActedByUserId or AuthorUserId.

The filtered grid as a CSV file, unpaged. Send the same body as feedback/list — Page and PageSize are ignored.

Example
curl -X POST "{dlp-api}/feedback/export" \
     -H "ClientGUID: 11111111-2222-3333-4444-555555555555" \

Attachment rules

Maximum files per submission5
Maximum size per file10 MB
Allowed extensions.png .jpg .jpeg .pdf .log
The file's contents are checked, not just its name. A renamed executable is refused even if it ends in .png. For .log, anything that is really an executable or a zip is refused.
Validation happens before anything is stored. If one file in a batch is refused the whole submission is refused and nothing is written — no half-saved feedback, no orphaned files. Fix the one file and resend.

Grid filter & sort keys

Filtering
WhereKeyBehaviour
fromDate / toDate—Window on RaisedOn. A bare date includes the whole day.
status top level—Single status. Equivalent to putting it in exactFilters; use whichever suits the UI.
search—One box, matched against Subject, Description, Raised By, Page / Module, the linked file name, and the readable id. FB-2052 and 2052 both find the same row. A literal % or _ matches itself.
exactFiltersFeedbackType, Impact, Source, Status, PageModule, RaisedByUserId, DisplayId / FeedbackNumber, AssignedToUserId, RaisedByRoleNameMulti-select. Values OR'ed within a key, keys AND'ed together: {"FeedbackType":["Bug","Question"],"Impact":["High"]} means (Bug or Question) and High. Numeric keys are sent as strings like the rest.
likeFiltersSubject, LinkedLog, LinkedLogFileName, LinkedLogActivity, LinkedLogApplication, RaisedByName, DisplayId, PageModule, Description, AssignedToName, RaisedByRoleName, plus the four vocabulary keysContains-match instead of exact, case-insensitive. Same OR / AND rule. One key per column is how the grid filters each column independently.
A single value may be sent as a scalar instead of an array — {"FeedbackType":"Bug"} works. An unrecognised key is ignored, not rejected, so a typo silently widens the results; check your key spelling against this table if a filter looks like it did nothing.
LinkedLog is the grid's Linked Log column, as one key. That column is rendered from three stored values — the file name for a transfer, the activity and the application for a blocked AI prompt — so no single column key can filter it. {"LinkedLog":["Prompt"]} matches any of the three; values within the key are OR'ed as everywhere else, so ["Prompt","png"] returns the prompt-linked rows AND the .png ones. The three individual keys still work when you want to be specific.
Two keys behave specially.
• DisplayId is not a stored column — "FB-2052" is rendered from FeedbackNumber — so the server reads the digits out of whatever you send: FB-2052, fb2052 and 2052 are the same id. In exactFilters it matches that one row; in likeFilters it is a contains-match on the number, so 205 finds FB-2052 and FB-1205. FeedbackNumber accepts the same two forms.
• RaisedByUserId is exact-match only. A contains-match on an int has no meaning, and a likeFilters entry for it is ignored. It is also not how you scope to one person — that comes from the token; use feedback/mine.
Sorting

SortBy accepts: RaisedOn default, FeedbackNumber, FeedbackType, Subject, Impact, Status, Source, PageModule, RaisedByName. With SortDescending true or false. Anything else falls back to RaisedOn descending, reported in AppliedSort.Resolved.

Sort the ID column by FeedbackNumber, not DisplayId — DisplayId is text and would order FB-999 after FB-1000. Text columns sort case-insensitively.
Paging

Page is 1-based; PageSize defaults to 25. Rows that share a timestamp are broken by FeedbackNumber descending, so no row ever appears on two pages or on none.

ExeApi V1 equivalents

The tray app points at the DLP-API host today and migrates to the Functions host later. Both routes already exist there, running the same service, so the migration is a base-URL change with no contract change.

DLP-API (today)ExeApi V1 (later)
POST {dlp-api}/feedback/submitPOST {exe-api}/V1/SubmitFeedback
GET {dlp-api}/feedback/lookupsGET {exe-api}/V1/GetFeedbackLookups
One difference, and it is in the headers. The Functions host identifies the caller with the agent scheme it already uses everywhere — Authorization: {ClientGUID}_{serialNumber} — instead of a separate ClientGUID header. The body, the fields, the validation and the response are identical.
The admin routes — list, detail, triage, export — stay on DLP-API and are not mirrored. The Functions host is agent-facing.

Deployment note

Two things have to happen before any of the above answers in an environment.

1 Run the Dlp migrationV0012__feedback.sql creates dlp."Feedback", dlp."FeedbackAttachment" and dlp."FeedbackComment" on every tenant database.
POST {dlp-api}/admin/migration/run?set=Dlp with the migration key, then check GET {dlp-api}/admin/migration/status.
2 Run the Common migration NEWV0002__feedback_permission_module.sql adds the FEEDBACK module with VIEW and EDIT and grants both to Admin. It is in the Common set because Module / Permission live in the tenant's user database, not the dlp schema.
POST {dlp-api}/admin/migration/run?set=Common.
Until this runs, GetModulesWithPermissions/1 has no Feedback module and the grid cannot be permission-gated — the role screen simply will not list it.
3 Register the APIM operationsEleven on the DLP API (the two feedback/mine verbs are new), two on the Exe API. A deployed route returns 404 until it exists in APIM — this is the usual cause of "the endpoint is missing".
Admin is matched on the role name containing "Admin", the same rule the Discovery routes use, read from the token and falling back to the user record. Provisioning creates Admin and User, so this holds for a standard tenant — but a customer who renamed their triage role to something without "Admin" in it will see only their own feedback in the grid. Worth checking the Role table before this reaches production. The FEEDBACK permission above is what eventually replaces the name match.
Storage. Attachments go to the feedback-attachments container in whatever the tenant's configured object store is — Azure Blob, S3 or a folder on disk. No per-tenant setup is needed; an unconfigured tenant falls back to the deployment's own storage settings.
