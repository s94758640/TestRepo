2. The protocol, as implemented

No deviations from §4. For the avoidance of doubt, this is what the server does:

DirectiontypeBehaviour
agent → ushelloAccepted and logged. No reply
agent → uspingAlways answered with {"type":"pong"}
us → agentpingNever sent. We only answer yours
us → agentServiceCommandOn an admin click, and on connect for every open command, oldest first
agent → usServiceCommandAckMoves the command to Acked
agent → usServiceCommandResultMoves it to Succeeded / Failed and stores every reported field
eitheranything elseIgnored, not an error — this is what lets us add message types later without breaking an older agent

Connection rules

  • One socket per serial, newest wins — a second connection for the same serial displaces and aborts the first.
  • Idle timeout 90 s. We drop a socket that sends nothing for that long, so your 30 s ping keeps it alive comfortably.
  • Frames capped at 64 KB; a larger one closes the socket with MessageTooBig.
  • A malformed frame is ignored, not fatal. We will not drop your connection over one bad message.

5. Decisions on our side (no agent impact)

DecisionWhy it does not affect you
Raw WebSocket, not SignalR Your frames are a string-named type sent bare; SignalR negotiates, handshakes, separates records and wraps an integer type in an envelope. Switching would have meant you rewriting the half that is already tested
Socket auth is ClientGUID + serial ownership CompanyGUID and X-Desktop-Client do not exist anywhere in our API, so there is nothing to validate them against. We check that the ClientGUID resolves to an active tenant and the serial is registered under it. Keep sending the other two if the agent already does
Cross-replica delivery Our API runs several instances, so a command can be created on one while your socket is held by another. Handled internally. Invisible on the wire
One open command per endpoint, enforced in the database Two admins clicking at the same instant cannot leave two commands racing to the agent. You still only ever receive one
commandId is 32-char lowercase hex Matches your sample. Opaque to the agent

6. When something does not work

Where to look first, by symptom:

SymptomMost likely cause
Upgrade gets 404 The agent's BaseUrl does not match what we registered on the gateway (§1)
Upgrade gets 401 ClientGUID missing or not an active tenant, or the serial is not registered under that client. We log which
Connects, then drops after ~90 s Pings are not arriving. We answer every one; we never send our own
Console shows the endpoint offline The serial on the socket does not match the stored endpoint serial — the case in the box above
Command stays on Delivered The ack or result is not reaching us. Check the commandId is echoed back exactly as sent
Result is accepted but the command does not finish The result's serial must match the command's. A mismatch is ignored deliberately, so one endpoint cannot close another's command

On a successful connection our logs record Endpoint {serial} connected. and, for each delivery, the command id, action and serial. Every command's full lifecycle — created, delivered, acked, completed, and the reported duration — is stored, so we can answer "what happened to this click" precisely.
